## 一、阶段 4 的定位：从「功能可用」到「生产可持续」

阶段 0–3 解决了「标注平台有没有这些能力」，阶段 4 解决「这些能力能不能长期在生产上稳定跑、算得清、看得见、扩得动」。

四个支柱：

| 支柱 | 目标 | 判定口径 |
|---|---|---|
| **A 可观测** | 出问题 5 分钟内能定位到域/端点/依赖 | SLO 指标可查、告警规则可触发、trace 可串联 |
| **B 可扩展** | 数据量 ×10 时关键路径不劣化 | 压测基线 + 索引覆盖 + 慢查询清单 |
| **C 可运营** | 运营能自助完成标注/质检/回流/成本核算 | 运营 SOP + 看板 + 误伤处置手册 |
| **D 可审计** | 任何数据进出可追溯 | 审计链完整、导出可复现（哈希一致） |

## 三、阶段 4 主线任务

### 4-1 可观测性（Observe）
- **SLO 指标**：标注提交成功率、派单延迟 p95、导出耗时 p95、回流受理成功率、Judge 调用错误率
- **告警规则**：错误率 > 阈值、p95 超预算、熔断触发数、outbox 积压、PG 连接数
- **trace 串联**：请求 ID → 应用用例 → 仓储 → outbox 事件
- **健康检查深化**：`/healthz` 分依赖项（PG/MinIO/Redis）子状态

### 4-2 性能与容量（Scale）
- 基于 P3-2 基线，建立 **性能预算表**（每端点 p95 上限）
- 慢查询清单 + 索引补齐（`pg_stat_statements` 若可用则用它，否则 `log_min_duration_statement`）
- 大表治理：`annotation_records` / `annotation_audit_logs` / `ai_token_usage` 的分区或归档策略评估
- 导出链路：大批量 SFT/DPO/PRM 导出的内存与流式写出验证

### 4-3 生产核验与发布纪律（Release）
- **迁移在生产上的实跑纪律**：先 `alembic upgrade --sql`（离线 SQL 审查）→ 在 PG 备份点后执行 → `downgrade` 验证可逆
- **特性开关清单**：所有新能力必须有开关 + 默认关闭 + 开启条件文档
- **回滚演练**：至少对 0082/0083/0084 做一次真实 downgrade→upgrade 往返

### 4-4 生态对接（Ecosystem）
- 训练平台导出 API：一键导出 SFT/DPO/PRM 的制品 + 清单（哈希、行数、资格门禁报告）
- 回流闭环验证：评测失败 → 回流 → 标注 → 导出 → 训练侧消费的**端到端演练**（prod 上做一次真实小样本）
- Webhook 出站（可选）：标注完成事件推给下游

### 4-5 运营闭环（Operate）
- 运营 SOP 集：标注排期、质检抽检、熔断误伤处置、回流受理、成本月报
- 看板：标注吞吐、质量（IAA/黄金题）、成本（Token + ROI）、数据飞轮（回流转化率）
- 误伤与申诉通道（熔断 PAUSED 的申诉路径）

## 四、阶段 4 验收（不设 staging 的等价保障）

因为没有 staging，用「三重等价」替代：

1. **离线等价**：迁移先出 `--sql` 全文审查；压测先 dry-run；写操作先 `EXPLAIN`/干跑
2. **可逆等价**：每个迁移在生产跑完立刻验 `downgrade` 往返（在事务外先做备份点）
3. **开关等价**：新能力默认关闭，先小流量开启、观察指标、再放量；异常一键回到旧行为

**阶段 4 完成的判定**：
- P3-1~P3-5 全部合并，遗留清单清零
- 性能预算表建立且首轮基线记录在案
- SLO 指标可查、告警能真触发（做一次人为触发验证）
- 端到端演练（回流→标注→导出）在生产真实跑通一次并留证
- 运营 SOP 与看板口径文档化
- 记忆库沉淀本阶段坑点，星云同步
