## 2. 各阶段交付内容

### 2.1 N2 — Canonical Schema 与 Adapter

**复用的既有能力**：`data-platform/` 的纯数据能力包、`RawAsset` 领域模型、
已有的对象存储 Canonical 键规范 `raw/{project_id}/{yyyy}/{mm}/{dd}/{asset_id}/content.{ext}`。

**新建**：`data-platform/ddp_data/adapters/{registry,builtin}.py`。

此前导入链路把 Hugging Face Human-1M 的解析**硬编码在 application 层**，
换一个来源就要改业务用例。现在拆成：

- `AdapterSpec`：来源类型、支持的字段、解析入口、版本，字段必须**穷尽声明**；
- `AdapterRegistry`：注册、发现、按来源选择；
- `parse_jsonl_rows` / `parse_human1m_preview`：把解码逻辑下沉到数据能力包。

**修复的真实缺陷**：`registry or build_default_registry()` 的 falsy 陷阱。
`AdapterRegistry` 实现了 `__len__`，空的注册表是 falsy，会被替换成默认表——
测试隔离因此失效，单测里注入的空注册表根本没用上。改为 `is None` 判断。

### 2.2 N3 — 多模态 Pipeline 与 Episode

三项交付：

**（1）多路媒体流同步偏差检测** —— `app/domain/episodes/sync_drift.py`，纯领域无 IO。
默认容差 40ms（`DEFAULT_TOLERANCE_NS = 40_000_000`）。基准流取起点最早者，
并列时按 `stream_id` 字典序，保证同一输入必得同一结论。

四态：`ALIGNED` / `EXCEEDED` / `UNKNOWN` / `SINGLE_STREAM`。

**这里有一处判断需要如实说明**：单机位片段（只有一条流）返回
`SINGLE_STREAM` 而**不判失败**。真实 HF 数据 demo_009/011/012 都只有单机位，
若把单流算作"同步未通过"，这些完全正常的数据会被打成不合格。这是数据形态
差异，不是质量问题。

**（2）切片规则注册表** —— `app/domain/episodes/segmentation_rules.py`。
规则按 `(rule_id, version)` 精确注册，未注册的版本显式抛
`SegmentationRuleNotRegisteredError`，不做"就近解析"。

修复：`SegmentationInput.__post_init__` 对源边界只做 `isinstance(int)`，
Python 整数无上限，`10**30` 能通过，被区间裁切后产出一条**看起来完全正常**
的窗口——脏数据静默伪装成正确结果。改为复用领域既有的 int64 校验。

**（3）`ingestion.job.created` 真正有 Worker 消费** —— `app/workers/ingestion_jobs.py`。
此前该事件被归为"留痕类"，写进 outbox 就完事，**没有任何进程会执行接入任务**：
接口返回 202，任务永远停在 QUEUED。现在改为投递类并补 Worker。

三个连带的真实 bug（真实执行才暴露，单测覆盖不到）：
- `actor_id=project_id` 不是合法 user（`updated_by` 外键指向 `users`）→ 改用 `job.created_by`；
- `IngestionJobService.apply_action` 不接受 `now` 参数（内部自取）→ 去掉传参；
- `_build_service` 把同一个 outbox 同时传给 audit 与 outbox → `'SqlOutboxRepository' object has no attribute 'record'`。

### 2.3 N4 — 标注与质量中心（PARTIAL）

见 §2.4（两个 worktree 合并后补写）。

### 2.4 N4 的边界说明

**AI 建议独立存储**改变了"AI 结果与人工结果同表同 JSONB"的既有形态，新增
`annotation_ai_suggestions` 表。**质量规则引擎**把此前只是字符串元数据、
"没有任何代码读取执行"的 `LabelDefinition.quality_rules` 变成可执行规则。

缺口（如实登记）：
- 质量规则的执行目前是**按需触发**，没有自动在标注提交时排队；
- AI 建议与人工修订的差异统计依赖 N7 的反馈闭环，尚未接线。

### 2.5 N5 — 数据资产与 Dataset 生命周期

**多维检索下推 SQL** —— `app/infrastructure/repositories/_json_array_predicates.py`。

关键安全点：JSON 数组谓词**全程使用 SQLAlchemy 表达式**，候选值走
`elements.c.value.in_(items)` 绑定参数，没有任何 f-string / `%` 拼进 SQL。
用真实 HTTP 打 `?scene_label='; DROP TABLE episodes; --` 返回 200 空结果，
不是 500 也不是全表。

跨项目隔离：`project_id == scope.project_id` 是硬条件，相关子查询也同时绑定
两侧 `project_id`。`test_filters_are_pushed_down_to_sql` 证明条件真的在 SQL 里
而非内存筛。

**元数据近重复检测** —— `app/domain/datasets/near_duplicate.py`。
三条件同时满足才判近重复：时间重叠率 + 时长相对差 + 场景标签一致。

**这里必须如实标注**：这是**元数据层面**的近重复，**不是视觉查重**。
两个不同场景、同一时长的片段不会被判重复。方法枚举值写作
`TEMPORAL_OVERLAP_V1` 而不是 `VISUAL_DUPLICATE`，就是为了不让人误读能力。

**DatasetVersion 血缘** —— 新建版本的节点要等 validate 转 READY 才登记，
因此 DRAFT 版本查血缘返回空图而不是 404（版本确实存在，报 404 会让客户端
误判成"版本被删或无权访问"）。

### 2.6 N6 — 训练集成与模型评测

`app/domain/datasets/requirement_match.py`，纯函数、无 IO、确定性。
三条硬规则写在模块头：

1. 同一 `(snapshot, facts, policy)` 必得完全相同的报告，落库后可按同输入复核；
2. **三态**：`PASSED` / `FAILED` / `UNVERIFIABLE`。`UNVERIFIABLE` 表示版本上
   没有可核对的事实，它**不是**通过。合并两者等于用"没检查"冒充"检查通过"；
3. 阈值不硬编码——业务阈值只来自需求快照，划分比例容差由部署配置显式传入。

**修复的最严重缺陷**：迁移 0038 的文档写明 `requirement_match` 已加入
`DELIVERY_IMMUTABLE_COLUMNS`、"应用层与触发器共用同一份清单，防止事后把
FAILED 改成 PASSED"，但**清单里根本没有这一列**。等于任何人可以直接
UPDATE 把 FAILED 改成 PASSED，绕开 N6 的全部阻断逻辑。已登记并补
`test_recorded_match_report_is_immutable` 守着（直接 UPDATE 必须被数据库拒绝）。

连带修了两处：
- 0038 的 downgrade 必然失败：该列是不可变触发器正文的一部分，SQLite 在
  `DROP COLUMN` 时校验触发器正文，引用已删列直接报错。改为先拆守卫再删列。
  根因是 `training_guards` 的 SQLite 语句是**模块级静态常量**，列清单写死，
  任何删列迁移都会留下"引用不存在列"的触发器——改为安装时按实际表结构生成。
- `new_training_delivery()` 把新参数写成必填，破坏所有既有调用方（两个既有
  单测直接 TypeError）。补默认值。

### 2.7 N7 — 模型反馈闭环

缺口统计接入真实 Episode 覆盖。三态计数：实测到 0 → `MEASURED` + 0；
无实测有人工 → `MANUAL`；两者都无 → `None` + `UNKNOWN`。

**核心防线**："没数据"不等于"覆盖率 0 已达标"。仓储对某维度值无 Episode
直接不返回该行，因此 0 与"测不到"在数据表示上可区分。

**修复的缺陷**：`MeasuredCoverage` 文档承诺"`measured_at` 为 None 时新鲜度
不得报 FRESH"，但实现只收集非空时间戳取最小值——缺时间戳的维度被跳过，
于是"一部分数据新鲜"被当成"整体新鲜"。实测复现：SCENE 5 分钟前 + ROBOT
无时间戳 → 报 FRESH。改为返回 `(anchor, incomplete)`，只要有一个有计数
无时间戳就整体 `UNKNOWN`。

**如实登记的局限**：`ACTION` / `LABEL` / `MODALITY` 三轴在 Episode 上没有
权威落点（`task_id` 是采集任务不是动作规格），只能走人工值 `MANUAL`，
缺口视图对这三轴无法给出实测结论。

### 2.8 N8 — 真实采集与设备集成（PARTIAL）

迁移 0007 给 `collection_tasks` 建了 `plan_id` / `sop_id` / `scenario_id` /
`action_spec_id` / `sop_version` / `action_spec_version` 六个可空列，
但**从未建过对应的四张表，也没有任何外键**。后果：这四个 UUID 可以写入
任意值——跨项目 ID、根本不存在的"幽灵引用"，数据库层完全无法拒绝。

迁移 0040 建四张表 + 给四个引用列补 `(project_id, xxx_id)` **复合外键**，
让"同项目"成为数据库可判定的事实。`NULL` 放行（合法的"未关联方案"），
非 `NULL` 必须存在且同项目。

三处真实缺陷：
- **版本一致性校验按 code 的版本谱系判定**：`sop_id=<v1 行> + sop_version="v2"`
  被判为一致，因为同 code 下确实有 v2 行——但 v2 是**另一行**。任务会带着
  自相矛盾的引用进入执行。改为只比对被引用行自身的版本列。
- **PATCH 是绕过版本校验的后门**：`sop_version` 在可改字段里但 PATCH 完全
  没校验，实测改成 `v9-nonexistent` 返回 200 并落库。已复用同一个校验函数。
- **迁移漏清"半截引用"**：清理条件只看四个引用列，漏掉"只有 `sop_version`
  没有 `sop_id`"的行，升级后残留正是应用层明确拒绝的组合。

缺口：素材目前只有 create/list/get，因此创建后状态永远是 `DRAFT`、
版本号不可演进，`ACTIVE` / `ARCHIVED` 枚举值当前**无法到达**。

### 2.9 N9 — 规模化运营与企业治理（PARTIAL）

**Prometheus 指标 + trace_id 贯通**。

指标标签只有 `method` / `path`（路由模板）/ `status`，真实请求实测：不同
UUID 归一到同一模板，`project_id` / `user_id` 不出现在响应体。补的是**白名单**
测试而非黑名单——任何人新增 `project_id` 标签会直接失败。

trace_id 三处同值：响应头 `X-Request-Id`、错误体 `error.request_id`、
`JsonFormatter` 输出的 `trace_id`。contextvar 用 token 复位，有用例证明不泄漏
到下一请求。

两处修复：
- **路由模板上限贴脸**：`MAX_TRACKED_ROUTES=200`，而真实应用已有 199 个可计数
  模板，只剩 1 个槽位，任何新增端点都会让后续路由静默折叠进 `__other__`，
  指标无声失真且无报错。改为 1000 并加余量护栏。
- **文档路由污染 `__unmatched__`**：`/docs`、`/redoc`、`/openapi.json` 是
  Starlette `Route` 而非 `APIRoute`，原实现让它们以 status=200 落进未匹配桶，
  使该桶同时混着"客户端乱猜的 404"和"服务端固定路径的 200"，404 率从此
  无法用于告警。已并入豁免。

缺口：`/metrics` 与 `/health` 一样**未鉴权**。指标不含项目/用户数据，但暴露
路由清单与流量规模，生产需靠反向代理限制来源网段。多基地、多供应商、经营
与治理**未涉及**，这是 N9 的绝大部分内容。

## 5. 契约缺口 —— 本轮已补齐（1.7.0 → 1.8.0）

合并完成后 `check_contract_parity.py --strict` 报 18 项新增差异。本轮按
`packages/contracts/README.md` 的版本化要求补到 **1.8.0**，全部为增量
（无路径删除、无字段删除、无必填性收紧）：

**新增 13 个端点**：
- `collection-plans` / `collection-sops` / `scenarios` / `action-specs`
  各「创建 / 列表 / 详情」共 12 个（`fragments/paths.stage8.yaml`）；
- `GET /datasets/{dataset_id}/versions/{version_id}/lineage`，复用既有
  `LineageResponse` 形状而非另立一套。

**补齐 2 个已实现但契约缺失的响应字段**：
- `training-deliveries[].requirement_match`（N6）：NULL = 未核对，
  **不等于通过**，落库后不可变；
- `data-gaps[].items[].coverage_source`（N7）：`MEASURED`/`MANUAL`/`UNKNOWN`，
  必须与 `current_count=null` 一起读——测不到不等于覆盖率为 0。

**错误码**：补登 `training_delivery_requirement_unmet`（N6 的三条拒绝路径）。

契约里如实写明了本批的两个边界，避免被误读成能力已完备：
- 采集素材**没有更新与删除端点**，因此状态恒为 `DRAFT`，
  `ACTIVE` / `ARCHIVED` 当前不可到达；
- 质量检查的 `passed` 是三态，`null` 表示该规则**对该记录没有结论**，
  客户端不得渲染成"通过"。

**未向 `parity-baseline.json` 添加任何豁免**——18 项差异是补契约消掉的，
不是标记"无害"跳过的。最终 `--strict` 通过。

剩余 6 项请求体差异 / 46 项响应体差异在基线内（`baseline` 里逐条写了为何无害），
本轮未新增。
