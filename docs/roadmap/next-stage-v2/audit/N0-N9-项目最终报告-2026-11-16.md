## 2. 主链贯通

```
HF 数据源 ──→ 导入任务 ──→ RawAsset（Canonical 层）──→ Episode
                                                        ├──→ 标注（Schema/任务/提交/质量检查）
                                                        └──→ 数据集版本（去重/划分/泄漏/质量 → FROZEN/VALID）
                                                                    └──→ 训练交付（需求核对 → 导出产物）
```

N0 时的实证是 `raw_assets=0 / episodes=0`。现在每一环都有真实数据流过，且全链可复现。

**外部数据接入**不只 HF：Adapter 注册表已支持第二种来源，新增来源只需注册适配器，
不改业务用例。

## 3. 各处能力摘要

### 3.1 数据接入（N1–N2）

- HF 数据源登记 → 导入任务（SAMPLE/SPLIT/FULL 三种范围）→ 媒体资产审看 → 人工审核；
- 导入产物同时登记为 `RawAsset(source_type=IMPORT)`，受不可变/禁删/去重保护；
- 解析器由 Adapter 注册表选择，不再硬编码。

### 3.2 处理与切片（N3）

- 多路媒体流同步偏差检测（容差 40ms，四态含 `SINGLE_STREAM`）；
- 切片规则注册表：`fixed-window` 与 `episode-boundary`，按 `(rule_id, version)` 精确注册，
  未注册版本显式拒绝；
- `ingestion.job.created` 有真实 Worker 消费（此前接口返回 202 但任务永远停在 QUEUED）。

### 3.3 标注与质量（N4）

- 质量规则引擎：4 条默认规则，阈值来自任务策略，`passed` 三态（`null` = 无结论）；
- **提交即自动质检**：结论与「提交冻结」同时可见；自动检查失败不否决提交
  （管理员配错策略不该让标注人无法提交）；
- AI 建议独立存储：模型身份（model_id / model_version / prompt_version）落库；
- **采纳统计**：ACCEPTED / REVISED / PENDING 三态，采纳率分母为已决定条数，
  无样本时为 `null` 而非 0。

### 3.4 数据集与血缘（N5）

- 多维检索下推 SQL（场景标签、质量状态、时间范围、设备等），参数化绑定，无字符串拼接；
- DatasetVersion 血缘：反向可查「这个版本用了哪些 Episode」；
- 元数据近重复检测（时间重叠 + 时长 + 场景标签），**不是视觉查重**，
  方法枚举写作 `TEMPORAL_OVERLAP_V1` 以免误读。

### 3.5 训练交付（N6）

- 交付时核对「已批准需求快照 ↔ 实际交付版本」，逐维度 expected/actual/status；
- 三态结论：`UNVERIFIABLE` 表示版本上没有可核对的事实，**不是通过**；
- 策略位 `on_failed` / `on_unverified` 各自可配 BLOCK 或 WARN；
- 核对报告落库后**不可变**（应用层与数据库触发器共用同一份清单）。

### 3.6 反馈闭环（N7）

- 数据缺口接入真实 Episode 覆盖统计；
- 三态计数：`MEASURED`（实测）/ `MANUAL`（人工）/ `UNKNOWN`（都不可得）；
- **测不到不等于覆盖率为 0**，`current_count=null` 与 `coverage_source=UNKNOWN` 必须一起读。

### 3.7 采集与设备（N8）

- 四类素材实体：采集方案 / SOP / 场景 / 动作库；
- `collection_tasks` 的四个引用列补了 `(project_id, xxx_id)` 复合外键——
  迁移 0007 建了这四列却从未建表、无外键，四个 UUID 可写任意值；
- 已有设备/校准/机器人管理（阶段 1）、采集任务与批次（阶段 2）。

### 3.8 运营与治理（N9）

- Prometheus 指标：标签白名单只有 method/path(路由模板)/status，无身份标识；
- trace_id 贯通：响应头、错误体、日志三处同值；
- 供应商档案、到货批次、片段裁决、只追加的验收账本、绩效指标；
- **跨供应商横向汇总**：本项目所有供应商的准时率/一次通过率/返工率/分段通过率，
  并如实给出「本期没交付的家数」。

### 5.2 部署过程中修掉的三个真实缺陷

这轮部署不是"跑一遍确认没事"，而是**真的跑出了三个问题**：

**（1）整套部署链路里没有任何一处执行 `alembic upgrade`**

镜像起来后数据库仍停在 `0034`，而代码要求 `0040`——新端点全部 500。
这类缺陷在「本地一直手动 upgrade 的开发机」上完全看不出来，只有全新环境才会暴露。

已新增独立的 `migrate` 服务（而不是塞进 api 启动脚本：多副本会并发跑同一个 DDL，
且迁移失败必须让 api 起不来）。api 与全部 worker 通过
`service_completed_successfully` 依赖它。

**（2）`maintenance-worker` 无限重启**

它的注释写着「默认不开」，但 `profiles: ["app"]` 让它随 app 启动；而
`maintenance_enabled=False` 时 worker 会立即退出，`restart: unless-stopped`
于是把它变成每几秒重启一次、日志刷 ERROR 的循环——看起来像故障，其实是配置
期望的行为。已改为独立 `maintenance` profile，需要备份时显式启用。

**（3）`.env` 的 `DDP_APP_VERSION=0.1.0` 覆盖了代码里的 0.2.0**

`/health` 与 `/platform/meta` 报的版本与镜像实际版本不一致。已同步。

### 5.4 部署步骤（可直接执行）

**本地/单机**

```bash
# 1. 准备配置（不要把真实密钥提交进仓库）
cp .env.example .env        # 若无 example，参照 .env 里的键名自行填写
#   必需：DDP_JWT_SECRET、DDP_S3_ACCESS_KEY、DDP_S3_SECRET_KEY（三者不得相同）

# 2. 启动基础设施
docker compose up -d postgres redis minio

# 3. 构建并启动应用栈（migrate 会自动先跑完）
docker compose --profile app up -d --build

# 4. 验证
curl -fsS http://localhost:8000/health
curl -fsS http://localhost:8000/api/v1/platform/meta
docker compose ps                            # 全部 Up，无 Restarting

# 可选：需要定时备份时再启用维护 worker
#   先在 .env 设 DDP_MAINTENANCE_ENABLED=true
#   docker compose --profile maintenance up -d maintenance-worker
```

**远端（staging）**

```bash
DDP_DEPLOY_HOST=<ssh 别名> DDP_DEPLOY_PATH=<目标仓库路径>   bash scripts/deploy-laptop.sh
```

脚本依次执行：确认目标仓库存在 → `git pull --ff-only` → `compose build` →
`compose up -d` → `/health` 检查。

## 10. 结论

**能用的部分是真能用的**：主链贯通不是示意图——真实 Hugging Face 数据走过完整的
HTTP 链路，落到可交付的数据集版本；每一处「通过」都有测试或实测值支撑。

**没做的部分诚实登记**：四个 PARTIAL 的具体缺口逐条列出，没有用「基本完成」
这类模糊表述掩盖。

**最重要的收获不是功能数量，而是修掉的那批「看起来存在但不生效」的缺陷**——
例如迁移文档声称某列已登记为不可变、实际清单里根本没有它；部署链路声称能起服务、
实际从没跑过迁移。这类问题不会让代码变红，只会让人在关键时刻发现系统没有想象中可靠。
