# DDP V3.1 总建设蓝图：端侧采集到训练数据集的真实闭环

## 1. 版本定位

V3.1 的核心不是增加一批孤立模块，而是把已有领域连接成一条真实可运行、可观察、可验收、可追溯的数据生产链。

```text
Robot / Sensor / Edge Capture
        ↓
CollectionTask / CaptureSession
        ↓
Edge Manifest + Local Spool
        ↓
Resumable Upload
        ↓
RawAsset / IngestionJob
        ↓
Adapter / Canonical / Processing Pipeline
        ↓
Episode / Media / Stream / Observation / Action
        ↓
Annotation Task Spec
        ↓
AnnotationTask Assignment（指定标注人）
        ↓
Annotation Console（人工标注）
        ↓
Auto QC → Human Review → Rework / Arbitration
        ↓
Accepted Episode + Accepted Annotation
        ↓
Dataset Builder
        ↓
DatasetVersion / Manifest / Hash / Freeze
        ↓
LeRobot / Canonical Export
        ↓
Training Request / External Training Handoff
```

## 2. 现有系统基线与事实约束

根据已提供审计材料，已知实现包括：
- React 18 + TypeScript + Ant Design + Vite；
- FastAPI + Pydantic v2 + SQLAlchemy + Alembic；
- PostgreSQL 16；
- MinIO / S3 兼容存储；
- DB Outbox + Worker（不是 Celery / Arq）；
- GitHub Actions；
- 设备、机器人、传感器、标定领域；
- Collection 领域；
- 预签名直传、分片上传、上传队列和存储服务；
- Episode 领域；
- Annotation 领域、任务/状态机/质量相关后端；
- Dataset 领域；
- Training Request、ModelOps、Inference / Evaluation 基础域；
- Hugging Face → LeRobot v3.0 → MinIO → HTTP Range 视频审看 → 人工审核后端 → 质量报告的真实数据验证。

审计中同时记录了以下关键缺口：
- 标注后端已存在，但完整标注控制台前端未完成；
- `/quality` 等部分前端导航仍是占位；
- HF 真实链路有验证证据，但 Parquet、ROS Bag / MCAP 等未凭空宣称支持；
- 外部训练 Adapter 曾为 503 占位，不能宣称真实训练已接通；
- 设备域存在部分 API / Domain / Contract / Audit / Outbox 一致性问题；
- 前端部分组件测试仅静态渲染，缺少交互测试；
- staging 在审计时受阻塞。

**本包必须先复核当前仓库，不能将审计快照直接当作今日代码事实。**

## 3. V3.1 目标与成功定义

### 3.1 必须实现的业务能力
1. 从至少一种真实机器人或端侧数据源生成 CaptureSession；
2. 将采集任务、设备、传感器、标定和原始文件建立关联；
3. 通过现有 MinIO/S3 上传能力完成可靠上传、断点续传和校验；
4. 解析原始数据并生成可审看的 Episode；
5. 基于指定 TaskSpec 生成标注任务；
6. 管理员/任务负责人能够把 AnnotationTask 指定给某个标注人；
7. 标注人进入个人工作台，查看媒体、按 Schema 标注并保存提交；
8. 质量规则自动检查标注结果；
9. 审核员通过、退回返工或仲裁；
10. Dataset Builder 只纳入符合规则的 Episode / Annotation Version；
11. 生成不可变 DatasetVersion、Manifest、Hash 和可校验导出包；
12. 记录训练交付引用，明确训练平台是否真实可用。

### 3.2 V3.1 Pilot 最小验收样本
建议以一个真实机器人/设备类型、一套真实传感器组合、一个 CollectionTask、一个 CaptureSession、至少 3 个完整 Episode 为 Pilot 起点。若硬件或数据条件不足，必须标记 BLOCKED，并使用真实导出文件做链路验证；不得把 Mock 数据称为硬件实测。

### 3.3 不作为 V3.1 强制范围
- 多城市、多基地、多供应商、商业结算；
- 机器人运动控制和安全控制闭环；
- 全量自动标注；
- 大规模训练集群调度；
- 多租户企业组织系统；
- 多机器人厂商所有 SDK 一次性全部适配。

## 4. 产品边界与用户角色

| 角色 | 主要工作 | 关键权限 |
|---|---|---|
| Platform Admin | 配置、账号、项目范围、设备接入 | 系统管理 |
| Data / Project Owner | 需求、采集任务、标注任务、Dataset | 项目内管理 |
| Collector | 查看采集任务、执行采集、上传数据 | 仅操作分配给自己的采集任务 |
| Annotator | 查看个人待办、标注、保存、提交 | 仅操作分配给自己的 AnnotationTask |
| Reviewer / QA | 抽检、审核、退回、仲裁 | 仅审核授权范围内结果 |
| Algorithm User | 查看 Dataset、提出训练需求、下载授权数据 | 只读资产/训练需求，按授权导出 |

当前只实现满足流程的最小角色和 ProjectScope 扩展，不建设复杂企业组织树。复用现有 Identity、ROLE_PERMISSIONS 和 ProjectScope，不另造第二套权限体系。

## 5. 领域对象关系

```text
Project
 ├─ DataRequirement
 ├─ Robot / Device / Sensor / CalibrationProfile
 └─ CollectionTask
      └─ CaptureSession
           ├─ CaptureManifest
           ├─ RawAsset[]
           └─ IngestionJob
                └─ ProcessingRun
                     └─ Episode[]
                          ├─ MediaAsset[]
                          ├─ Stream[]
                          ├─ Observation / Action
                          ├─ QualityRun
                          └─ AnnotationTask[]
                               ├─ TaskSpecVersion
                               ├─ Assignment
                               ├─ AnnotationResultVersion[]
                               └─ Review / Rework
                                    ↓
                                DatasetItem
                                    ↓
                                DatasetVersion
                                    ↓
                                ExportJob
```

### 5.1 三种 Task 必须分清
- **CollectionTask：** 采集任务，定义采什么、用什么设备、什么场景动作、采集数量和 SOP。
- **AnnotationTask：** 标注工作单，定义对哪些 Episode/Clip 按哪个 LabelSchema 版本做什么标注，并分配给谁。
- **Dataset / Training Request：** 数据集构建和训练需求，不是标注工作单。

LeRobot 的 `task_index` / task instruction 是数据语义字段，不等于 DDP 的 CollectionTask ID 或 AnnotationTask ID。必须通过显式关联保存映射，不得混用 ID。

## 7. 架构原则

- 后端保持现有模块化单体和领域分层；Edge Agent 是部署在采集工作站的轻量独立进程，不等于把后端拆成微服务。
- 复用现有 Collection、Devices、Ingestion、S3、Outbox、Episodes、Annotation、Datasets、Identity、ModelOps。
- 新增能力优先作为既有领域内的子模块或 Adapter。
- 大文件处理继续走异步 Worker；HTTP 只负责创建任务、查询状态和轻量元数据。
- Raw 原始数据不可覆盖；Processed / Labeled / Dataset 都是可追溯衍生对象。
- 所有状态转换在 Domain / Application 层执行，前端只展示可执行动作。
- API、OpenAPI、前端类型、Client、测试同步更新。
- GitHub 是唯一代码托管与 CI/CD 平台；VS Code + Claude Code CLI + 原生 Agent。

## 8. V3.1 实施阶段

| 阶段 | 主题 | 关键交付 |
|---|---|---|
| N0 | 当前仓库复核与基线冻结 | Capability Matrix、API/DB/UI 地图 |
| N1 | 设备/采集任务与 CaptureSession 贯通 | Task → Session → Device/Sensor |
| N2 | Edge Capture Agent | 本地采集、Manifest、Spool、Preflight |
| N3 | 上传与 RawAsset 闭环 | 断点续传、校验、入库、事件 |
| N4 | Adapter / Canonical / Episode | 至少一个真实格式进入标准模型 |
| N5 | AnnotationTask 创建与指定分配 | TaskSpec、Assignment、My Queue |
| N6 | Annotation Console | 标注工作台、自动保存、提交 |
| N7 | QC / Review / Rework | 质量规则、审核、返工、仲裁 |
| N8 | Dataset Builder / Version / Export | 合格样本构建、冻结、Manifest、导出 |
| N9 | 端到端 Pilot / Hardening | 真实链路证据、恢复测试、安全和性能 |

N0–N9 是依赖顺序，不代表必须完全串行。可并行开发独立 UI / 文档 / 测试，但共享 Schema、Migration、OpenAPI 由单一 Owner 管理。

## 9. 最终验收定义

一个真实采集 Episode 必须能够从 `CollectionTask` 追溯到 `CaptureSession`、Robot / Device / Sensor、RawAsset、ProcessingRun、Episode、AnnotationTask、Assignment、AnnotationResult、ReviewRecord、DatasetVersion 和 ExportJob。

任何一个环节缺失，都不能宣称“端到端闭环完成”。
