## 3. 三条硬约束（三处同时强制）

这三条同时写在 **OpenAPI schema、Pydantic 模型、数据库 CHECK**，任一层都不放过：

| 约束 | 理由 | OpenAPI | Pydantic | DB |
|---|---|---|---|---|
| `revision` 必须是 40 位十六进制 commit sha | `main` 会移动；只存分支名的导入不可复现 | `pattern: ^[0-9a-f]{40}$` | `Field(min_length=40, max_length=40, pattern=...)` | `CHECK (length(revision) = 40)` |
| `access_condition=GATED` 必须配 `is_gated=true` | 防止"标成公开、实际要申请"导致合规误判 | 见 `AccessCondition` 描述 | 领域 `__post_init__` 抛错 | `CHECK gated_consistency` |
| `scope=SAMPLE` 必须给 `sample_limit` | 默认小样本，不默认全量下载（`docs/ddp/07` §1） | 描述说明 | 领域校验 | `CHECK sample_scope_requires_limit` |

许可证缺失时 Adapter 返回 `None` 而非猜测；`fail` 动作必须带 `error_message`
（失败留痕是 `docs/ddp/07` §5 的硬要求）。

## 4. 状态机

```
PENDING ──start──> RUNNING ──succeed──> SUCCEEDED (终态)
   │                   ├──fail──────> FAILED    (终态)
   └──cancel───────────┴──cancel────> CANCELLED (终态)
```

- 终态之后任何动作返回 `state_transition_invalid`（409）；
- `PENDING` 不能直接 `succeed`：必须先 `start`，否则"开始时间"与"确实跑过"无法区分；
- `allowed_actions` 由服务端计算并随响应返回，前端只按此渲染按钮。

## 5. 兼容性与变更流程

- 基线 SHA256 受 CI 强制：改动基线与 `.sha256` 必须同批且经评审；
- `--check` 用 oasdiff `--fail-on ERR` 检查破坏性变更；
- 新增字段保持向后兼容；删除/重命名字段、收窄枚举、收紧 `required` 属破坏性变更，
  必须新版本化（`ddp.stage7/1.1.0`）并在本文件追加变更记录。
