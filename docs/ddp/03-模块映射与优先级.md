# DDP 模块映射与迭代优先级

## 1. 模块决策方式

对照目标架构检查现有系统，每个模块只能进入以下一种主要处理方式：

- **保留**：现有能力稳定且满足需求，不改动。
- **优化**：功能存在，但体验、性能、质量或可维护性需要提升。
- **补齐**：主体已存在，缺少必要子流程或边界能力。
- **集成**：优先接入成熟工具或 SDK，不自研通用引擎。
- **新增**：审计确认确实不存在，且有明确业务需求。
- **暂缓**：当前阶段没有必要或依赖未满足。
- **废弃**：确认不再使用，需有迁移与批准方案。

不得仅因目标架构图中出现某模块，就直接新增该模块。

## 2. 优先级规则

| 优先级 | 判断标准 | 处理方式 |
|---|---|---|
| P0 | 阻塞当前主流程、数据安全或核心正确性 | 优先修复 |
| P1 | 当前 MVP 闭环必需 | 当前迭代建设 |
| P2 | 提升效率、可维护性或扩展性 | 排入后续版本 |
| P3 | 长期经营或规模化能力 | 暂缓至业务验证后 |

## 3. 建议的当前阶段顺序

1. 仓库审计、运行基线和测试基线。
2. 现有数据源接入能力检查。
3. Hugging Face 数据源登记与小样本导入。
4. 文件校验、缓存和导入任务状态。
5. Episode / Video / Metadata 解析。
6. 视频审看、样本导航和时间轴。
7. 人工审核与审核记录。
8. 基础质量报告。
9. Dataset Version 与导出。
10. 标注工具集成和更完整的数据治理。

上述是建议顺序，最终以现有代码和依赖关系为准。

## 4. 暂不默认实施

- 真实机器人运动控制；
- 完整供应商排产系统；
- 完整财务、发票和自动结算；
- 企业级多租户 SaaS；
- 自研通用标注引擎；
- 自研视频播放器内核；
- 自研分布式训练框架；
- 微服务拆分和 Kubernetes 化。

只有在实际业务、性能或组织规模证明有必要时再立项。
