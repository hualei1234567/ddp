# DDP 代码质量与架构治理规范

## 1. 基本原则

- 单一职责、明确边界、低耦合。
- 先理解现有模式，再按项目既有风格实现。
- 优先复用，不复制粘贴相同业务逻辑。
- 以可测试、可维护、可追溯为目标，不为抽象而抽象。

## 2. 必须避免

- 巨型组件、巨型服务、巨型函数；
- Controller / Route 中堆叠复杂业务逻辑；
- 万能 Utils / Common 文件不断膨胀；
- 循环依赖和跨模块直接访问内部实现；
- 多处重复实现同一业务规则；
- 业务状态和机器人型号散落硬编码；
- 空 catch、吞异常、无边界重试；
- 未使用代码、死代码和无意义兼容层；
- 为单一调用场景设计过度复杂的通用框架；
- 未经评估引入新的数据库、消息队列或微服务。

## 3. 模块边界

每个业务模块应明确：
- 对外提供什么能力；
- 拥有哪些核心实体；
- 对外 API / Service 契约；
- 可以依赖哪些模块；
- 不允许直接访问哪些内部实现。

跨模块交互优先通过公开 Service、API 或事件契约，不直接修改其他模块内部数据结构。

## 4. 配置与环境

- 密钥、Token、密码不得提交到 Git。
- 环境配置沿用仓库既有方式。
- 不在代码中硬编码本地绝对路径。
- 不将大体积数据、缓存和模型权重提交到仓库。
- 示例配置不得包含真实凭据。

## 5. 测试要求

- 核心业务规则有单元测试。
- API 有适用的集成测试。
- 关键用户流程有端到端或等效验证。
- Bug 修复应添加回归测试。
- 不允许通过删除测试、放宽断言或跳过失败来制造绿色结果。

## 6. 重构门槛

重构前必须说明：
1. 当前问题和证据；
2. 不重构的实际风险；
3. 影响范围；
4. 兼容方案；
5. 测试保护；
6. 回滚方式。

只做当前任务必要的重构。大范围重构需要单独任务和用户批准。
