# DDP 持续迭代治理文件包 V1.0

本文件包用于**已经开发一部分的 DDP 系统持续迭代**。它不是新项目脚手架，不会要求重建工程，也不代表当前仓库已经具备全部目标能力。

## 一句话原则

**以现有代码为事实基线，以目标架构为演进方向；先审计、再规划、后增量开发；保留成果、优先复用、禁止推倒重来。**

## 如何使用

### 第一步：备份现有项目

在现有 DDP 仓库中确认 Git 状态，提交或备份当前稳定成果。不要在有未确认改动的工作区直接做大规模修改。

### 第二步：放入项目根目录

解压后，将文件包内的目录和文件合并到现有 DDP 仓库根目录。

- 如果仓库**没有** `CLAUDE.md`，直接放入。
- 如果仓库**已经有** `CLAUDE.md`，先比较内容，将本文件包中的 DDP 规则合并进去，禁止直接覆盖原文件。
- `docs/ddp/`、`prompts/ddp/`、`templates/ddp/` 可与现有文档并存。
- GitHub 模板可按需复制到仓库 `.github/` 对应目录；若已有模板，合并而不是覆盖。

### 第三步：首次只做审计

打开 `prompts/ddp/01-首次只读审计Prompt.md`，发送给 Claude Code。

首次任务必须只读：
- 不修改业务代码；
- 不执行数据库迁移；
- 不删除文件；
- 不重建项目；
- 不自动安装或升级依赖；
- 不推送或合并代码。

先得到现状审计报告和迭代计划，再由你确认开发范围。

### 第四步：逐模块迭代

每次只选择一个边界清楚的模块或任务，使用：
- 新功能：`02-单模块增量迭代Prompt.md`
- Bug：`03-Bug修复Prompt.md`
- 架构评审：`04-架构评审Prompt.md`

每个任务都要有范围、文件所有权、验收标准、测试和回滚方案。

## 文档状态标识

- `VERIFIED`：有代码、运行或测试证据证明。
- `PARTIAL`：已有部分实现。
- `UNVERIFIED`：代码存在，但未证明可用。
- `MISSING`：审计后确认缺失。
- `BLOCKED`：受环境、权限或外部依赖限制。
- `PLANNED`：目标规划，尚未实现。
- `DEPRECATED`：已废弃，不应继续作为执行依据。

**禁止把规划能力描述成已上线能力。**

## 重要边界

1. 本文件包定义的是治理规则和目标业务架构，不是对当前仓库技术栈的判断。
2. 前后端框架、数据库、ORM、任务队列、存储、部署方式，以现有仓库审计结果为准。
3. GitHub 是当前代码管理基线；不再把 GitLab 作为默认执行方案。
4. 当前阶段以个人开发、测试、验证为主，优先使用 Hugging Face 上许可和访问条件明确的公开第一人称数据集。
5. 不在 MVP 阶段擅自接入真实机器人运动控制。
6. 优先复用现有 DDP 功能、官方 SDK 和成熟开源项目，不重复造轮子。
