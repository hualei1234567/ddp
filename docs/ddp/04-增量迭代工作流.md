# DDP 增量迭代工作流

## 1. 标准流程

`需求澄清 → Git 状态检查 → 现状定位 → 复用评估 → 影响分析 → 方案确认 → 最小实现 → 测试回归 → 文档更新 → 验收交付`

## 2. 开发前必须回答

1. 当前功能在哪里实现？
2. 是否已有相似页面、组件、API、服务或数据表？
3. 为什么现有能力不能满足本次需求？
4. 能否通过配置、扩展或 Adapter 完成？
5. 本次要修改哪些文件？
6. 会影响哪些路由、API、数据库、权限和用户流程？
7. 如何验证成功？如何回滚？

回答不清楚时先调查，不要直接写代码。

## 3. 变更范围控制

每个任务必须明确：
- 目标和非目标；
- 修改文件白名单或预期范围；
- 依赖模块；
- API / Schema 契约；
- 数据库影响；
- 测试范围；
- 验收标准；
- 风险和回滚方案。

开发中发现范围扩大时，暂停并向 General Owner 汇报，不得悄悄扩展任务。

## 4. 数据库变更

- 使用仓库已有 Migration 机制。
- 先检查历史 Migration 和生产兼容性。
- 优先采用向后兼容的增量变更。
- 删除列、改名、数据重写等破坏性变更必须单独审批。
- 提供备份、迁移验证和回滚方案。
- 未经批准不连接或修改生产数据库。

## 5. API 变更

- 先检查调用方和现有契约。
- 保持兼容；需要破坏性变更时采用版本化或过渡方案。
- 统一字段命名、错误语义、分页和权限校验。
- 记录单位、时区、枚举值和空值含义。
- 不允许前端通过隐藏按钮替代后端授权。

## 6. 前端变更

- 优先复用现有 Design System、组件和布局。
- 不另建平行 UI 框架。
- 页面只负责展示和交互，不承载复杂数据解析或核心业务规则。
- 保持加载、空、错误、无权限和成功状态。
- 关键操作提供确认、反馈和防重复提交。

## 7. 后端变更

- 业务规则放在合适的服务 / 领域层。
- Controller / Route 负责协议适配，不堆叠业务逻辑。
- 外部系统调用通过现有集成层或薄 Adapter。
- 长耗时任务按现有异步机制执行。
- 异常需要记录上下文并向调用方返回可处理错误。

## 8. 完成定义

任务只有在以下条件满足后才能标记完成：
- 需求范围实现；
- 相关测试已执行；
- 关键回归通过；
- 无已知高严重度问题；
- 文档已同步；
- 真实变更和测试证据已汇报。
