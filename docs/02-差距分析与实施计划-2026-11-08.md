# DDP 差距分析与实施计划

> 日期：2026-11-08
> 依据：`docs/DDP_具身智能数据闭环平台建设总规范_V1.0_FINAL.md`（唯一建设基线）
> 说明：桌面 `memory/` 仅作参考；凡与本文档冲突，以 `docs/` 下规范为准。
> 范围：首期按用户指定的主链路收敛——**机器纳管 → 数据采集 → 数据上传 → 数据标注 → 数据训练**。

---

## 1. 总体判断

DDP 是绿地建设。规范定义了 16 个领域模块，但**不能一次全部开工**。首期只做一条可验收的端到端链路：

```text
项目/权限基础
  → 机器人/设备/传感器纳管
  → 采集方案/SOP/任务/现场工作台
  → 上传/接入/完整性校验/原始资产登记
  → Episode 切片（基础）
  → 标注 Schema/任务/工作台/审核
  → 数据集构建/版本冻结/LeRobot 导出
  → 训练需求/交付引用
```

质检、资产目录、模型闭环、供应商、基地运营、经营分析在链路打通后按阶段接入；首期只保留**必要的最小质量门禁**（上传完整性、Episode 有效性、标注审核、数据集冻结校验）。

## 3. 目标技术架构（待用户确认 ADR）

### 3.1 推荐栈

| 层 | 选型 | 理由 |
|---|---|---|
| 后端 | Python 3.11 + FastAPI + Pydantic v2 | 规范要求 Python 类型标注；生态适合数据处理 |
| ORM/迁移 | SQLAlchemy 2 + Alembic | 成熟、可审查迁移 |
| 数据库 | PostgreSQL 16 | 关系数据、JSONB、事务、索引 |
| 缓存/队列 | Redis 7 + Celery（或 Arq） | 异步 Job、租约、重试 |
| 对象存储 | S3 兼容（MinIO 本地 / 云 OSS） | 大文件不入业务表，符合 §6.7 |
| 前端 | React 18 + TypeScript strict + Ant Design 5 + Vite | 企业后台信息密度、表格/筛选/抽屉组件成熟 |
| 测试 | pytest + httpx + Playwright + ruff + mypy/pyright | 单元/接口/契约/E2E |
| 容器 | Docker Compose（本地/测试/单机 staging） | 首期不引入 K8s |
| 观测 | 结构化日志 + Prometheus 指标 + OpenTelemetry Trace | 符合 §23 |
| CI/CD | GitHub Actions | 规范强制 GitHub 为唯一平台 |

> 这是一项需要用户批准的决策（`ADR-001`）。如果用户更希望与 MaterialDev 统一为 Vue 3 + Element Plus，可在批准前替换前端栈；后端不受影响。

### 3.2 架构形态

- **模块化单体 + 异步 Worker**，不拆微服务（规范 §3.1）。
- 分层：`api → application → domain ← infrastructure`；`workers` 独立入口。
- 领域模块按规范 §14.3 组织；跨模块只走公开 Application API / Contract / 事件。
- 所有外部系统（机器人、标注工具、训练平台、对象存储、身份源）通过 Port/Adapter。
- 多格式解析用 Parser 注册表；多设备用 Adapter/Strategy。
- 首期单库多项目，所有查询强制服务端 `project_id` 隔离（§16.4）。

### 3.3 仓库目录

严格采用规范 §14.2 的 monorepo 结构：

```text
ddp/
├── apps/web/
├── backend/app/{api,application,domain,infrastructure,workers,shared}
├── data-platform/{ingestion,parsers,canonical,processing,quality,annotation,dataset}
├── packages/{api-client,contracts,ui,utilities}
├── integrations/{robots,sensors,annotation-tools,training-platforms,storage}
├── infra/{docker,monitoring,deployment,scripts}
├── docs/{product,architecture,data-standards,api,adr,operations,testing,reports}
├── scripts/
├── .github/{workflows,ISSUE_TEMPLATE,PULL_REQUEST_TEMPLATE.md,CODEOWNERS}
├── README.md
└── CHANGELOG.md
```

首期不创建空目录；目录在对应模块开工时创建，避免形式主义（§14.3）。

### 3.4 数据分层与 Canonical

按规范 §6.2：

```text
Raw → Canonical → Processed → Labeled → Dataset → Training/Evaluation
```

- 原始数据不可被处理结果覆盖。
- Canonical Schema 版本化；LeRobot 只是交换格式之一。
- 时间同步、坐标系、单位、标定版本必须显式记录（§6.4–6.5）。
- 大文件存对象存储，数据库只存元数据/引用/Hash/状态/血缘（§6.7）。

## 4. 阶段计划（按主链路收敛）

> 每个阶段都必须有：范围冻结 → 任务卡 → 实现 → 测试 → 交付验收 → 证据归档。
> 阶段未验收，不进入下一阶段（规范 §24 阶段门禁）。
> 时间估算为「1 个主会话 + 1+6 Agent 协作」的参考区间，真实工期取决于决策与真实设备/数据可用性。

### 阶段 0（基建，2–3 天）

**目标：** 让后续开发有仓库、有 CI、有契约、有环境、有团队、有任务。

- **DDP-000** 初始化 Git 仓库、目录骨架、`.gitignore`、`.editorconfig`、`README.md`、`CLAUDE.md`、`AGENTS.md`。
- **DDP-001** 建立 GitHub 仓库、`main` 分支保护、CODEOWNERS、PR 模板、Issue 模板。
- **DDP-002** 搭建后端骨架：FastAPI 应用工厂、配置、统一异常、结构化日志、健康检查、`/api/v1/platform/meta`。
- **DDP-003** 搭建前端骨架：Vite + React + TS strict + AntD + 路由 + 请求封装 + 基础布局。
- **DDP-004** 本地基础设施：`docker-compose` 起 PostgreSQL、Redis、MinIO；`make dev` 一键启动。
- **DDP-005** 契约体系：`packages/contracts`（OpenAPI + JSON Schema）、前端类型生成、契约测试基线。
- **DDP-006** CI 基线：lint、format、type check、unit test、build、secret scan、dependency scan。
- **DDP-007** 数据库基线：Alembic 初始化、迁移规范、测试库隔离。
- **DDP-008** 平台纳管：注册 `ddp` 项目、1+6 团队、worktree、任务板、知识库、评测套件、发布记录。
- **DDP-009** Agent 定义：`.claude/agents/{general-owner,product-manager,system-architect,ux-designer,frontend-engineer,backend-engineer,qa-devops}.md`。
- **DDP-010** ADR 基线：技术栈、模块化单体、数据分层、项目隔离、存储、权限、测试、部署。
- **DDP-011** 安全基线：密钥管理、`.env` 禁入仓、依赖扫描、上传白名单设计。
- **DDP-012** 可观测基线：request_id、结构化日志、指标端点、错误码规范。

**验收：**
- CI 在空骨架上全绿。
- `make dev` 能起本地环境，`/health` 200。
- 平台中 `ddp` 项目可见，7 角色、任务、知识条目可查。
- 所有 ADR 经用户批准。

### 阶段 1（项目基础 + 机器纳管，7–10 天）

**目标：** 先让「机器/设备/传感器」可管、可查、可校准，为采集提供真实对象。

- 身份与权限：登录、用户、角色、项目角色、服务端 RBAC（§19）。
- 项目：项目 CRUD、成员、项目上下文、服务端隔离（§16.4）。
- 设备档案：机器人、设备、传感器、固件、序列号、能力描述、状态、位置、Owner（§5.2–5.3）。
- 校准记录：标定配置、版本、有效期、关联传感器（§5.3）。
- Adapter 契约：`discover/connect/disconnect/get_status/get_capabilities/get_metadata/start_capture/stop_capture/health_check/calibration_info`；不支持能力返回 `Unsupported`（§5.4）。
- 设备运维：预约、领用/归还、巡检、故障、维修、停用（§5.5，首期最小）。
- 前端：设备列表/详情/分组、能力矩阵、标定记录、状态徽标。
- 测试：权限越权、项目隔离、设备状态机、Adapter 契约、重复序列号唯一约束。
- 真实证据：至少 1 个模拟 Adapter + 1 份设备样例（无真机也可验收契约，真机验收另记）。

**验收：** 真实/模拟设备可登记、可查、可标定、可被权限隔离；设备域 API 契约冻结。

### 阶段 2（采集 + 上传接入，10–14 天）

**目标：** 打通「任务下发 → 现场采集 → 上传 → 校验 → 原始资产登记」。

- 数据需求：需求单、版本、验收标准（§4.1，最小）。
- 采集方案：场景、动作、视角、设备/传感器配置、采集参数、SOP（§4.2–4.4）。
- 采集任务与批次：状态机、人员/设备/场地分配、排期、领取、执行、暂停、恢复、异常、提交（§4.5）。
- 采集员工作台：任务、SOP、开工检查、上传、自检、返工；弱网恢复与上传进度（§4.5、§18.3）。
- 上传：分片、断点续传、幂等、大小/类型/签名校验、Hash（§17.1）。
- 接入：文件校验、元数据提取、格式探测、完整性检查、隔离区（§6.6）。
- 原始资产：RawAsset 登记、对象存储引用、Hash、大小、格式、来源任务/设备/人员（§6.7）。
- Episode：基础切片、起止时间、关联任务/设备/传感器、状态（§7.2）。
- 看板：今日任务、执行中、已完成、原始数据量、有效 Episode（§4.6，最小口径）。
- 测试：任务状态流转、设备分配冲突、上传中断/恢复、重复上传、文件格式异常、时间同步、Episode 边界、项目隔离。
- 样例数据：至少 1 套多相机 + 机器人状态样例包（可用合成数据）。

**验收：** 一份真实/样例数据从任务到 Episode 全链路可追溯；原始文件不被覆盖；失败可定位。

### 阶段 3（标注 + 最小质检，10–14 天）

**目标：** 让 Episode 可被标注、审核、返工，并形成可用标签。

- 标签 Schema：版本化、前端不写死（§8.1）。
- 标注项目/任务：领取、进度、提交、审核、返工、仲裁（§8.2）。
- 标注工作台：多路视频、时间轴、Episode 边界、标签编辑、帧标记、保存/提交（§7.3、§8）。
- 审核与抽检：通过/驳回、问题类型、返工次数、复检（§9.3）。
- 最小自动质检：上传完整性、Episode 有效性、时间同步偏差、必填标签缺失（§9.1–9.2）。
- AI 辅助标注：首期只留接口与占位，不接模型（§8.3 后续）。
- 测试：标注 Schema 版本、审核路径、返工闭环、权限、并发保存、时间边界。
- 证据：1 个标注任务从创建到审核通过的完整记录。

**验收：** 标注结果可版本化、可审核、可追溯；不合格数据不能进入数据集。

### 阶段 4（数据集 + 训练支撑，7–10 天）

**目标：** 把有效 Episode 变成可复现、可授权、可导出的数据集版本，并交付训练。

- 数据集：创建、筛选、去重、划分、质量报告、冻结、导出、复现（§10.2）。
- 数据集版本：样本清单、Schema、标签、质量规则、Pipeline、划分策略、Manifest、Hash、创建人/时间（§10.3）。
- 数据血缘：RawAsset → Episode → Annotation → DatasetVersion → Training（§10.4、§6.2）。
- 导出：LeRobot 格式（规范要求作为交换格式之一）、Manifest 校验（§6.3、§11.2）。
- 训练需求：目标、模型类型、数据/场景/动作、质量阈值、格式、交付时间（§11.1）。
- 训练交付：ExportJob、交付单、接收方、验收状态、返工（§12.4 最小）。
- 训练平台集成：Adapter 接口；首期可 mock，但必须标记 mock（§11.3）。
- 测试：冻结后不可静默修改、数据泄漏检查、重复样本、导出校验、血缘正向/反向追溯。
- 证据：1 个 DatasetVersion 冻结 + 1 次 LeRobot 导出 + 1 次训练交付记录。

**验收：** 算法团队可拿到可复现、可追溯、可授权的数据集版本；训练引用可回溯。

### 阶段 5（质检/资产/模型闭环，后续）

- 质检规则引擎、自动检测、抽检、仲裁、返工报告。
- 资产目录、检索、复用、保留策略。
- 模型登记、推理、评测、失败反馈 → 新数据需求。
- 运营指标与成本。

### 阶段 6（规模化，后续）

- 多基地、多供应商、多团队、产能/成本、资源调度、稳定性治理。

## 5. 全流程质量与交付管理

### 5.1 完成定义（DoD）

严格区分（规范 §22.3）：

| 状态 | 含义 | 证据 |
|---|---|---|
| Code Complete | 代码写完 | 分支、提交、PR |
| Test Passed | 测试通过 | CI 日志、测试报告 |
| QA Accepted | QA 独立验收通过 | 交付记录、验收结论 |
| User Accepted | 用户确认 | 平台交付验收 |
| Released | 已发布 | 发布记录、健康检查 |

未执行测试标 `NOT RUN`；环境阻塞标 `BLOCKED`；失败必须如实报告，不得用「应该没问题」代替证据。

### 5.2 测试体系（规范 §22.1）

- 单元测试：领域规则、状态机、值对象、Parser。
- 接口测试：FastAPI TestClient/httpx，覆盖权限、校验、错误码。
- 契约测试：OpenAPI/JSON Schema 与前端类型一致。
- 集成测试：数据库、对象存储、队列、迁移。
- 文件处理测试：MCAP/ROS bag/HDF5/MP4 解析、时间同步、切片。
- 权限测试：越权读写删、跨项目泄漏、IDOR。
- E2E：采集→上传→标注→数据集主链路；Playwright。
- 性能：大文件上传、列表分页、导出。
- 安全：路径穿越、恶意上传、SQL 注入、XSS、SSRF、Secret 泄漏。
- 恢复：备份恢复演练。

### 5.3 CI 阶段（GitHub Actions）

1. `lint`：ruff、eslint、prettier。
2. `type`：mypy/pyright、tsc。
3. `unit`：pytest 单元。
4. `integration`：PostgreSQL/Redis/MinIO service containers。
5. `contract`：OpenAPI 校验 + 前端类型生成 diff。
6. `build`：后端镜像、前端构建。
7. `e2e`：Playwright（关键链路）。
8. `security`：依赖扫描、Secret 扫描、SAST。
9. `migration`：Alembic 升级/回滚检查。
10. `release`：打标签、产物、变更日志。

### 5.4 发布与回滚

规范流程（§23.4）：

```text
feature 分支 → 本地/CI 测试 → PR → Code Review → 合并 main
→ staging 部署 → 回归验收 → 生产审批 → 生产部署
→ 健康检查 → 发布确认或回滚
```

平台映射：
- `POST /api/projects/ddp/releases` 建发布记录；
- `validate` → `evaluation` → `request-approval` → `publish`；
- `canary` → `observe` → `promote` 或 `rollback`；
- 每次发布必须关联 Dataset/API/Schema 变更与回滚方案。

### 5.5 可观测性（§23）

- 结构化日志：`request_id`、`trace_id`、`project_id`、`task_id`、`episode_id`、`dataset_id`、`job_id`。
- 指标：API 可用性/延迟/错误率、队列积压、Worker 健康、上传失败、处理耗时、导出失败。
- 告警：错误率、积压、存储、磁盘。
- 审计：登录、权限变更、上传、下载、导出、发布、删除。

### 5.6 安全（§19）

- 默认拒绝、最小权限、服务端 RBAC + 项目范围。
- 文件上传白名单 + 内容签名 + Hash + 隔离区。
- 下载审计；敏感数据脱敏；Secret 不入库不入仓。
- 删除/迁移/发布等不可逆操作：先 dry-run、逐条确认、带计数、先备份（沿用历史事故硬规则，作为工程纪律，不作为规范依据）。

### 5.7 数据与迁移

- 所有 Schema 变更走 Alembic；迁移可审查、可回滚或可补偿。
- 大对象只存对象存储；数据库存元数据。
- 数据集版本冻结后不可静默修改；变更创建新版本。
- 原始数据不可被处理结果覆盖。

## 6. Agent 平台映射（全流程管理）

| 管理环节 | 平台能力 | DDP 用法 |
|---|---|---|
| 项目 | `agent_projects` / `/api/projects` | 注册 `ddp`，仓库指向 `~/vscodeworkspace/DataPlatform` |
| 团队 | `standard-1-6` / team preview/apply | 7 角色，按规范 §21.1 |
| 任务 | tasks + 状态机 + DAG | `DDP-000` 起，按阶段建任务与依赖 |
| 分工 | assignee + worktree | FE/BE 独立 worktree；PM/Arch/UX/QA 只读 |
| 执行 | dispatch plans/items | 可执行任务自动排队；人工确认后 run |
| 交付 | deliveries/review/validate | 每阶段交付单 + 证据 |
| 测试 | eval suites/datasets/runs | 单元/接口/E2E/安全/性能套件 |
