# DDP 具身智能数据闭环平台建设总规范

## 产品规划、业务架构、数据标准、代码架构、工程治理与实施路线

> 项目：DDP（Embodied AI Data Platform）\
> 执行环境：macOS + VS Code + Claude Code CLI\
> Agent 协作：Claude Code 原生 Agent 协作\
> 并行研发：Git Branch + Git Worktree\
> 代码托管：**GitHub（唯一代码托管与版本管理中心）**\
> 文档性质：产品、架构、研发、测试、部署、运维和验收统一基线。

------------------------------------------------------------------------

# 0. 文档控制与执行边界

## 0.1 建设目标

本文件统一整合 DDP
的产品规划、业务模块、数据闭环、机器人适配、技术架构、代码目录、反屎山代码规范、Agent
分工、GitHub 工作流、测试、安全、部署和阶段路线。后续
PRD、技术设计、代码实现、测试用例和验收报告必须能够追溯到本规范或经批准的变更记录。

## 0.2 产品定位

DDP 是面向具身智能行业的数据生产、治理、资产化和训练支撑平台。它不是普通
CRUD 后台、单纯文件上传工具，也不是某个机器人或单个采集基地的定制系统。

平台必须支持多项目、多机器人、多传感器、多数据格式、多基地、多供应商和多种训练数据需求。

## 0.3 项目背景与首批适配对象

业务适配对象包括如下
天机机器人、Ego-centric、UMI、无本体数据和第三方生态数据。它们是首批适配对象，不得硬编码成系统唯一支持对象。

## 0.4 工具与代码管理约束

-   使用 macOS、VS Code、Claude Code CLI。
-   使用 Claude Code 原生 Agent 协作能力。
-   使用 Git Branch + Git Worktree 并行开发。
-   GitHub 是唯一代码托管、版本管理、代码审查和 CI/CD 平台。
-   使用 GitHub Repositories、Branches、Commits、Pull
    Requests、Issues、Actions、Releases、Tags、CODEOWNERS。
-   禁止建立 GitHub 与 GitLab 双重代码托管体系；GitLab
    不作为本项目代码托管或 CI/CD 平台。
-   不再引入 DSH / DeepSeek Harness。
-   不使用 Codex 作为本项目执行环境。
-   不得未经批准更换现有模型服务、Runtime、数据库、对象存储和部署设施。

## 0.5 已有系统保护

先审计现有仓库和业务，不得直接推倒重建。不得无依据更换技术栈、删除已有能力、重命名公共
API、破坏数据库字段、修改生产数据、执行破坏性 Migration
或部署生产变更。代码存在不等于功能可用，Mock 不等于真实业务，Agent
自述不等于验收证据。

## 0.6 规范优先级

用户明确批准的决策 \> 本规范的安全与阶段门禁 \> 已批准 ADR \> 已批准 PRD
和技术设计 \> 仓库已验证约定 \>
未经批准的临时实现。发生冲突必须提交差异、影响和建议，不得自行选择。

# 1. 产品愿景与数据闭环

## 1.1 核心业务链路

``` text
算法/业务数据需求
  → 需求分析与采集方案
  → 场景、动作、设备、SOP 规划
  → 项目与采集任务
  → 人员、机器人、设备、场地调度
  → 现场采集与数据上传
  → 原始数据接入和完整性校验
  → 格式解析、时间同步、Episode 切片
  → 清洗与预处理
  → 人工标注 / AI 辅助标注 / 自动标注
  → 自动质检 / 人工抽检 / 仲裁返工
  → 数据资产登记与版本冻结
  → 训练集构建与标准格式导出
  → 算法训练 / 模型评测 / 推理验证
  → 模型问题与数据缺口分析
  → 反向生成新的采集和标注需求
```

## 1.2 建设目标

  领域   目标                                 可验证结果
  ------ ------------------------------------ ------------------------
  采集   场景、动作、SOP、任务和执行标准化    任务可下发、执行可追踪
  接入   多机器人、多传感器、多格式统一接入   原始数据可校验、可登记
  处理   多模态解析、同步、切片、清洗         形成标准 Episode
  标注   人工、AI 辅助、自动标注协同          标注可审核、可版本化
  质检   自动规则、抽检、仲裁、返工           问题可定位、可闭环
  资产   元数据、标签、版本、血缘、检索       数据可复用、可复现
  训练   数据集构建、划分、导出、反馈         算法团队可稳定获取数据
  模型   模型登记、推理、评测、反馈           模型问题可反向驱动数据
  运营   人员、设备、基地、供应商、成本       产能和质量可量化

## 1.3 产品边界

DDP
重点负责数据生产、数据治理、数据资产和训练数据支撑。算法团队已有的训练集群、训练调度、机器人厂商控制系统、第三方标注平台、对象存储和企业身份系统，应优先通过接口集成，不得未经评估重复建设。

# 2. 业务领域与核心对象

## 2.1 领域模块

1.  Project Management：项目管理。
2.  Requirement Management：数据需求。
3.  Collection Management：采集方案、场景、动作、SOP、任务。
4.  Device & Robot Management：机器人、设备、传感器、标定。
5.  Data Ingestion：上传、接入、原始资产登记。
6.  Data Processing：解析、同步、清洗、切片。
7.  Episode Management：Episode、Frame、Observation、Action。
8.  Annotation：标注任务、标签 Schema、审核。
9.  Quality Management：规则、检测、问题、返工。
10. Data Asset & Dataset：资产目录、数据集、版本、血缘。
11. Training Integration：训练需求、数据导出、训练引用。
12. Model & Inference Integration：模型登记、推理、评测。
13. Base & Workforce Operations：基地、人员、场地和产能。
14. Supplier & Delivery：供应商、交付和验收。
15. Analytics：运营分析和经营看板。
16. Identity & Administration：身份、权限、配置和审计。

## 2.2 核心对象

Project、DataRequirement、CollectionPlan、Scenario、ActionSpec、SOP、CollectionTask、CollectionBatch、Episode、Robot、Device、Sensor、CalibrationRecord、RawAsset、IngestionJob、ProcessingJob、AnnotationTask、Annotation、LabelSchema、QualityRule、QualityRun、QualityIssue、Dataset、DatasetVersion、DatasetItem、DataLineage、TrainingRequest、ExportJob、Model、ModelVersion、InferenceJob、EvaluationResult、Supplier、Delivery、AuditLog。

每个领域必须明确业务 Owner、核心实体、数据所有权、API
边界、事件边界、权限边界、依赖关系和测试责任。禁止所有业务逻辑堆到一个巨大
Service、Controller 或 ORM Model 中。

## 2.3 状态机

核心实体必须定义状态机、合法转换、前置条件、执行角色、失败处理和审计要求。示例采集任务：

``` text
DRAFT → PENDING_REVIEW → APPROVED → READY → ASSIGNED
→ IN_PROGRESS → SUBMITTED → DATA_CHECKING
→ ACCEPTED → COMPLETED

DATA_CHECKING → REJECTED → REWORK → SUBMITTED
IN_PROGRESS → PAUSED / BLOCKED / CANCELLED
```

最终状态以现有系统核验后冻结。前端不得任意修改状态字段。

# 3. 总体技术架构

## 3.1 架构原则

优先采用清晰分层、领域模块化、契约优先的架构。默认优先评估"模块化单体 +
异步任务
Worker"。只有真实业务规模、团队边界、部署隔离或性能瓶颈证明有必要时，才拆分微服务。禁止为了追求复杂度而过早微服务化。

## 3.2 逻辑架构

``` mermaid
flowchart TB
  U[采集员 / 标注员 / 管理者 / 算法人员]
  FE[Web 前端与作业工作台]
  API[API / BFF]
  IAM[身份认证与权限]
  APP[Application 用例编排]
  DOMAIN[Domain 领域模块]
  WORKER[异步 Worker / Pipeline]
  INFRA[Infrastructure 适配层]
  DB[(关系数据库)]
  OBJ[(对象存储)]
  CACHE[(缓存)]
  MQ[消息队列 / 事件]
  EXT[机器人 / 标注 / 训练 / 模型系统]
  OBS[日志 / 指标 / Trace / 审计]
  U --> FE --> API --> IAM --> APP --> DOMAIN
  DOMAIN --> INFRA
  DOMAIN --> MQ --> WORKER --> INFRA
  INFRA --> DB
  INFRA --> OBJ
  INFRA --> CACHE
  DOMAIN --> EXT
  API --> OBS
  DOMAIN --> OBS
  WORKER --> OBS
```

## 3.3 分层职责

-   **Presentation：** 页面、交互、表单、视图状态、API
    调用；不承载权威业务规则。
-   **API / Application：**
    请求校验、身份上下文、用例编排、事务边界、DTO 转换、统一异常。
-   **Domain：**
    实体、值对象、状态机、业务规则、领域服务、领域事件；不依赖
    Web、ORM、消息队列和云 SDK。
-   **Infrastructure：** Repository 实现、对象存储、消息队列、外部系统
    Adapter、文件处理和 SDK。
-   **Worker / Pipeline：** 大文件处理、视频转码、MCAP/ROS bag
    解析、Episode 切片、质检和数据集导出。耗时任务不得长期占用 HTTP
    请求线程。

## 3.4 模式选择

-   简单 CRUD：Application Service + Repository。
-   复杂状态：状态机 + 领域服务。
-   多厂商设备：Adapter / Strategy。
-   多格式解析：Parser 注册机制。
-   多步骤处理：Pipeline / Job。
-   外部系统：Port / Adapter。
-   异步通知：领域事件或集成事件。
-   重复请求：幂等键 + 唯一约束。
-   复杂跨系统流程：按实际需要评估 Saga / 补偿。
-   CQRS、Event Sourcing、微服务均非默认选项，必须有真实收益和 ADR
    依据。

# 4. 数据采集中心

## 4.1 项目和需求

项目字段应覆盖名称、编码、类型、客户/供应商、负责人、周期、目标数据量、预算、交付标准、成员和风险。

数据需求应覆盖业务目标、模型背景、机器人类型、场景、动作、视角、传感器、数据量、质量阈值、标签、训练用途、优先级、交付时间和验收标准。需求变更必须版本化。

## 4.2 采集方案

方案包含场景定义、动作脚本、动作阶段、成功条件、失败条件、视角、设备选型、传感器配置、采集参数、标定要求、数据格式、SOP、质量标准和安全要求。

## 4.3 场景与动作库

场景可覆盖家庭、工业、仓储、桌面、厨房、物品整理、抓取放置、开关门抽屉、工具使用、双手协作、人机交互、复杂遮挡和动态环境等。

动作定义包含编码、名称、说明、前置条件、关键步骤、成功判据、失败模式、难度、适配机器人、适配设备、标签
Schema 和版本。

## 4.4 SOP

每份 SOP
必须包含目标、设备、设备检查、场景布置、标定、操作步骤、采集参数、注意事项、成功标准、异常处理、数据提交和自检清单。任务执行时记录所用
SOP 版本。

## 4.5 采集任务与现场工作台

支持任务创建、批次拆分、人员/设备/场地分配、排期、领取、执行、暂停、恢复、异常、上传、提交、质检、返工和完成。

采集员工作台支持查看任务、SOP、动作要求、设备要求，完成开工检查、采集、异常记录、数据上传、自检和返工。现场端必须考虑弱网恢复、上传进度、清晰错误提示和尽量短的操作路径。

## 4.6 采集运营看板

展示今日任务、待执行、执行中、已完成、原始数据量、有效
Episode、有效时长、不合格率、人员产能、设备利用率、场地利用率、项目进度和异常。每个指标必须有计算口径和数据来源。

# 5. 机器人、设备与传感器纳管

## 5.1 适配原则

首批适配智元精灵
G1/G2、Franka、ARX、灵犀、Ego-centric、UMI、无本体和第三方数据。必须采用可配置设备类型、能力描述和
Adapter，不得在核心业务代码中大量堆积型号 if/else。

## 5.2 设备档案

建议记录
device_id、type、vendor、model、serial_number、firmware_version、hardware_version、calibration_profile、capability_profile、status、location、owner
和维护记录。字段命名以现有代码规范为准。

## 5.3 传感器

支持
RGB、RGB-D、深度、IMU、关节状态、末端执行器、力/力矩、手部/身体动作捕捉、音频等。记录型号、序列号、采样频率、分辨率、内外参、坐标系、同步方式、固件和标定版本。

## 5.4 Adapter

统一设备适配接口按设备能力支持
discover、connect、disconnect、get_status、get_capabilities、get_metadata、start_capture、stop_capture、health_check、calibration_info。不支持的能力必须明确返回
Unsupported，不得伪造成功。

## 5.5 运维

支持预约、领用归还、巡检、故障、维修、标定、固件版本、利用率、生命周期和停用管理。

# 6. 多模态数据接入与 Canonical 标准

## 6.1 格式适配

重点支持或评估 MCAP、ROS
bag、rosbag2、HDF5、MP4、MOV、PNG/JPEG、WAV、CSV、JSON、Parquet、LeRobot
和厂商自定义格式。格式解析必须通过 Parser / Adapter
注册，不得散落在业务代码中。

## 6.2 分层数据

``` text
Raw：原始文件、原始消息、原始时间戳、原始元数据
  ↓
Canonical：统一实体、时间、坐标系、单位、传感器、Episode Schema
  ↓
Processed：清洗、同步、切片、校验和衍生产物
  ↓
Labeled：标注结果、标签版本、审核和质量结论
  ↓
Dataset：数据集、版本、训练/验证/测试划分
  ↓
Training / Evaluation：训练引用、模型版本、评测和反馈
```

原始数据不可被处理结果覆盖。

## 6.3 Canonical Schema

至少覆盖
Project、Robot、Device、Sensor、Session、Episode、Frame、Observation、Action、Timestamp、CoordinateFrame、Calibration、Annotation、QualityResult、Dataset、DatasetVersion
和 DataLineage。

Schema 必须版本化，具备兼容和迁移策略。LeRobot 是训练交换格式之一，不是
DDP 内部唯一数据模型。

## 6.4 时间同步

必须考虑设备时间、主机时间、ROS 时间、Unix
时间、单调时钟、时区、偏差、漂移、采样频率、丢帧和延迟。保留原始时间语义、标准化时间和转换依据，不得只保存一个无法解释的时间戳。

## 6.5 坐标与单位

明确世界、机器人基座、末端执行器、相机、IMU
和关节坐标系；明确左右手约定、旋转表达、长度、角度、速度、加速度、力和力矩单位。变换必须有来源和版本。

## 6.6 完整性检查

接入时检查文件大小、Hash、格式、可解析性、文件数量、传感器通道、时间范围、连续性、采样频率、关键字段、设备关联和
Episode 完整性。不合格文件进入隔离区，不得直接进入可训练数据集。

## 6.7 存储原则

大体积视频、图片和机器人数据存对象存储；关系数据库保存元数据、文件引用、Hash、大小、格式、存储位置、权限、版本、处理状态和血缘。禁止把大体积视频二进制直接写入普通业务表。

# 7. 数据处理与 Episode

## 7.1 Pipeline

``` text
Upload → File Validation → Metadata Extraction → Format Parsing
→ Time Alignment → Calibration Validation → Episode Segmentation
→ Data Cleaning → Quality Pre-check → Artifact Registration
```

每个 Pipeline 必须有 ID、Version、输入/输出
Schema、参数、依赖、执行环境、资源要求、超时、重试、幂等、日志、指标、失败原因、产物引用和血缘。

## 7.2 Episode 管理

支持 Episode
创建、起止时间、关联任务和设备、传感器、视频片段、机器人状态、动作指令、语言指令、场景标签、任务结果、成功/失败、质量状态、标注状态和版本。切片规则必须可配置、可复现和版本化。

## 7.3 数据预览

支持多路视频、时间轴、机器人状态曲线、关节曲线、末端位姿、IMU、动作指令、标签、质量问题和同步偏差。大文件采用代理文件、抽帧或流式读取，避免一次性加载完整原始文件。

------------------------------------------------------------------------

# 8. 标注中心与自动标注

## 8.1 标注类型

任务级、Episode
级、时间片段、动作阶段、技能、语言指令、物体/场景、成功失败、失败原因、接触状态、机器人状态、人机交互状态及项目自定义标签。

标签由版本化 Schema 管理，不得写死在前端。

## 8.2 标注管理

支持标注项目、规范、Schema、任务、人员、领取、进度、提交、审核、返工、仲裁和交付。

优先评估 Label Studio 等成熟工具。集成时明确任务同步、数据访问、Schema
映射、结果回传、身份、权限、版本、Webhook 和失败重试。DDP
必须保留标注结果的权威记录。

## 8.3 AI 辅助与自动标注

支持视频摘要、动作片段建议、场景识别、任务阶段识别、语言指令建议、异常片段检测、标签建议、置信度和人工确认。

AI
结果必须记录模型、模型版本、Prompt/配置版本、生成时间和置信度。低置信度和高风险类别进入人工复核，不得将模型生成结果直接当作验收标签。

## 8.4 自动标注治理

规则版本化、模型登记、置信度阈值、人工复核比例、抽样准确率、人工修订记录和效果趋势必须可追溯。

------------------------------------------------------------------------

# 9. 数据质量管理

## 9.1 质量维度

-   采集：任务完成度、完整性、设备状态、清晰度、视角、动作有效性、场景符合度、SOP
    遵循。
-   技术：可解析性、时间同步、丢帧、采样频率、传感器异常、标定、坐标系、连续性。
-   标注：准确性、完整性、时间边界、一致性、规则遵循和复核通过率。
-   训练：任务/场景/动作/视角覆盖、多样性、失败案例、数据泄漏、重复样本和标签噪声。

## 9.2 质量规则

每条规则包含 Rule
ID、Version、适用数据、适用项目、检测逻辑、阈值、严重级别、处理建议、Owner
和生效时间。规则必须可测试和版本化。

## 9.3 质检闭环

``` text
提交 → 自动质检 → 抽样复核
             ├─ 通过 → 验收
             └─ 不通过 → 问题归因 → 返工 → 复检 → 验收
```

报告展示检测量、通过量、不通过量、不合格率、问题类型、责任环节、返工次数、复检结果和趋势。

# 11. 训练支撑、模型与反馈

## 11.1 训练需求

# 15. 反屎山代码与工程质量强制规范

## 15.1 核心原则

代码必须可理解、可测试、可维护、可扩展。不得用"快速交付"为理由持续累积结构性技术债务。代码行数少不代表质量高，抽象层数多也不代表架构优秀。

## 15.2 禁止巨型文件和巨型函数

-   单文件接近 500 行必须触发评审。
-   超过 800 行原则上必须拆分；例外须在 PR 说明。
-   单函数原则上不超过 50 行有效逻辑。
-   超过 80 行必须评估拆分。
-   不允许通过拆成大量无意义小文件规避复杂度。
-   Controller、Service、Component 不得无限膨胀。

以上为评审阈值，不是机械硬限制。

## 15.3 禁止万能模块

禁止无限扩张
`utils`、`common`、`helpers`、`base_service`、`manager`、`misc`、`shared`。公共模块必须有明确职责、Owner
和稳定复用价值。

## 15.4 禁止循环依赖

-   Domain 不得依赖 Infrastructure。
-   领域模块不得导入其他模块内部实现。
-   跨模块调用通过公开 Application API、Contract 或事件。
-   禁止用动态 import、全局变量或隐式注册隐藏循环依赖。

## 15.5 禁止复制粘贴业务逻辑

同一业务规则不得在多个模块分别实现。抽取共性前先确认规则稳定且真正共享，避免为了消除少量重复而创建过度通用框架。

## 15.6 禁止硬编码

不得硬编码机器人型号、传感器类型、格式映射、业务状态、质量阈值、标签
Schema、文件路径、外部地址、Token、密码和项目专属规则。配置必须有明确来源、校验、默认值和版本策略。

## 15.7 禁止吞异常

禁止空
`except`、只打印错误后继续、返回成功掩盖失败、未知状态默认成功、用空数组掩盖业务错误。异常必须分类、记录必要上下文、正确传播并给出可处理错误信息。

## 15.8 禁止不安全数据库操作

禁止拼接用户输入 SQL、跨模块随意写表、绕过事务、无 Migration 改
Schema、未经批准删除生产数据。多表状态更新必须明确事务边界。

## 15.9 禁止无约束异步任务

禁止无限重试、无超时、无幂等、无状态、无失败记录和把大文件处理放在普通
HTTP 请求线程。任务必须有 Job
ID、输入输出、状态、重试、超时、错误码、日志和幂等键。

## 15.10 禁止前端业务逻辑膨胀

前端不承担权威权限校验，不直接实现复杂数据库规则，不让页面组件同时承担请求、状态机、数据转换和复杂计算。API
Client 必须统一封装。

## 15.11 禁止无依据抽象和过早微服务化

不得为一次性逻辑设计复杂工厂和多层继承，不为尚不存在的业务建设插件系统，不因追求架构"高级"而引入微服务、CQRS、Event
Sourcing。所有复杂技术选型必须有 ADR 和实际收益依据。

## 15.12 必须遵守的设计规范

-   单一职责；
-   高内聚、低耦合；
-   依赖倒置；
-   显式依赖；
-   类型安全；
-   统一异常；
-   统一配置；
-   结构化日志；
-   清晰事务；
-   幂等；
-   自动化测试；
-   文档同步。

Python 使用类型标注；前端使用 TypeScript
严格模式（若当前技术栈支持）；外部数据进入领域层前必须校验。避免滥用
`Any` / `any`。

## 15.13 复杂度治理

圈复杂度超过 10、嵌套超过 3
层、单模块依赖过多、函数布尔参数泛滥、状态隐式传递、重复实现多套业务规则时，必须触发评审。优先使用
Guard Clause、提取函数、状态映射和边界重整。

## 15.14 技术债务

每项债务登记 Debt
ID、位置、描述、影响、风险、根因、修复建议、Owner、计划版本和状态。禁止长期用
TODO / FIXME 代替债务管理。

## 15.15 重构规则

重构前必须有测试保护；一次重构聚焦明确范围；不得混入无关功能；保持外部行为不变（除非需求明确变化）；大规模重构必须先提交
ADR；不得为了"优雅"重写稳定且无问题的模块。

## 15.16 Code Review 检查清单

-   领域边界是否清楚；
-   是否重复实现业务规则；
-   是否存在循环依赖；
-   是否有巨型文件/函数；
-   是否硬编码；
-   是否吞异常；
-   是否处理事务和幂等；
-   是否存在权限绕过；
-   是否泄漏敏感信息；
-   是否有必要测试；
-   API / Schema 是否兼容；
-   是否具备日志、指标和回滚方案；
-   文档和技术债务是否更新。

# 16. API、数据库与事件契约

## 16.1 API

每个 API 明确 Endpoint、Method、Request/Response
Schema、错误码、认证、权限、项目范围、分页、排序、幂等、兼容策略和限流要求。优先沿用现有项目风格，不得混用多套不一致规范。

## 16.2 版本兼容

破坏性变更必须版本化；新增字段优先保持兼容；明确废弃周期；不得无通知删除字段或改变字段语义。

## 16.3 数据库

统一表字段命名；核心表有
Owner；业务主键与外部标识区分；时间字段语义明确；状态使用枚举；合理设置唯一约束和索引；大对象存对象存储；Migration
必须可审查并有回滚或补偿方案。

## 16.4 项目隔离

所有项目数据由服务端校验 Project Scope。不得信任客户端
project_id。查询、更新、删除、下载、导出、搜索和缓存均须校验权限。缓存
Key 包含必要项目上下文。跨项目共享必须显式授权。防止 IDOR。

## 16.5 事件

事件包含
event_id、event_type、event_version、occurred_at、producer、aggregate_id、project_id（适用时）、correlation_id
和 payload。消费者必须幂等。不得将事件总线当成无约束远程函数调用。

# 17. 文件、异步任务与 Pipeline 工程规范

## 17.1 文件安全

上传必须校验类型白名单、大小、文件名、内容签名、Hash、权限和存储路径。支持分片、断点续传、幂等、失败重试、上传会话过期、恶意文件扫描和下载审计。不得只依赖扩展名判断格式。

## 17.2 Job

每个 Job 具备 Job
ID、类型、输入引用、输出引用、状态、创建人、创建/开始/结束时间、重试次数、超时、取消能力（如支持）、错误码、错误摘要、日志和幂等键。

## 17.3 重试

设置最大次数和退避策略，区分可重试与不可重试错误。外部副作用必须有幂等保障。防止重复处理产生重复资产或交付。

## 17.4 Pipeline 版本

处理逻辑变化必须生成 Pipeline Version。已处理数据可追溯
Parser、Processing、Configuration、Schema 和 Model Version。

# 19. 权限、安全与数据保护

## 19.1 角色建议

Manager、Annotator、Quality Inspector、Data Engineer、Algorithm
Engineer、Device Operator、Supplier Manager、Auditor、Read-only Viewer。

## 19.2 安全原则

-   默认拒绝、最小权限；
-   平台角色 + 项目角色 + 资源授权；
-   文件访问和下载审计；
-   客户数据隔离；
-   敏感数据脱敏；
-   Secret 安全管理；
-   数据保留和删除策略；
-   备份加密；
-   高风险操作审批。

## 19.3 安全测试

覆盖越权读写删、跨项目泄漏、文件路径穿越、恶意上传、SQL
注入、XSS、CSRF（适用时）、SSRF、不安全反序列化、Secret 泄漏、API
滥用和备份泄漏。

# 20. GitHub 代码管理与研发协作

## 20.1 唯一平台

GitHub 是 DDP
唯一代码托管、版本管理、代码审查和自动化工作流平台。禁止建立双重代码托管体系。

## 20.2 分支策略

-   `main`：稳定、可发布分支；
-   `develop`：仅在现有发布流程确有需要时启用；
-   `feature/<name>`：功能开发；
-   `fix/<name>`：缺陷修复；
-   `hotfix/<name>`：紧急修复；
-   `release/<version>`：按需启用。

不为形式维护不必要的长期分支。

## 20.3 Commit

使用 Conventional Commits：

``` text
feat: 新增采集任务管理
fix: 修复文件上传校验
refactor: 拆分数据处理服务
docs: 更新数据标准
test: 增加 Episode 质量测试
perf: 优化数据集检索
build: 更新构建配置
ci: 优化 GitHub Actions
security: 修复项目权限校验
```

## 20.4 Pull Request

PR 包含关联需求、背景、变更范围、设计说明、数据库变化、API/Schema
变化、测试命令和结果、安全影响、风险、回滚方案和文档更新。

## 20.5 GitHub Actions

至少配置 Lint、Format、Type Check、Unit Test、Integration
Test、Build、Dependency Scan、Secret Scan、Migration
Check、容器构建（适用时）、发布和部署前检查。

生产部署必须使用受保护 Environment、审批和最小权限凭据。

## 20.6 Worktree

每个 Agent 任务使用独立分支和 Worktree，明确
Owner、允许修改目录和交付范围。共享
API、Schema、权限中间件、Migration、全局路由和设计系统必须先冻结契约并指定唯一
Owner。禁止多个 Agent
无协调修改共享文件。未经批准不得强推、重写历史、删除分支或部署。

## 20.7 GitHub 安全

Secrets、依赖安全扫描和访问权限复核。不得提交
`.env`、Token、密码和客户敏感数据。

# 27. 最终产品定义

DDP
是一套以数据需求为起点、以采集执行为入口、以多模态处理为基础、以标注和质检为质量保障、以数据资产和训练集为核心产出、以模型训练和评测反馈为闭环驱动、以设备和基地运营为生产保障的企业级具身智能数据闭环平台。

最终必须做到：

1.  一个系统管理多个数据项目；
2.  一套标准适配多种机器人和传感器；
3.  一条链路贯通采集、处理、标注、质检和训练；
4.  一个统一标准承接多种原始格式；
5.  每份数据有来源、版本、质量和血缘；
6.  每个训练集可复现、可追溯、可授权；
7.  每个模型问题可反向形成数据需求；
8.  每个生产环节可量化效率、质量和成本；
9.  每个代码模块有边界、Owner、测试和维护责任；
10. 每次发布有审查、证据、监控和回滚方案。

**最终标准不是"系统开发完成"，而是平台能够持续、稳定、可控地生产高质量具身智能训练数据，并以真实业务结果证明其价值。**
