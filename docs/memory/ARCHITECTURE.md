# DDP 记忆系统架构设计（Memory Nebula）

- 版本：v1.0 · 2026-11-24
- 状态：**PROPOSED**（设计已定，待用户确认后建库）
- 目标：把项目积累的**踩坑点 / 错误点 / 影响点**变成**可检索、可执行、可演进**的约束资产
- 存储：文件为**权威源**（进 git，可 review、可 diff、可随分支演进）+ OpenViking 为**检索层**（跨会话召回）

---

## 一、为什么需要这个系统（本项目实证）

### 1.1 现状缺口（S0 式实测）

| 项 | 实测结果 |
|---|---|
| 专属踩坑/教训文档 | **0 个**（`find docs -iname "*lesson*\|*pitfall*\|*踩坑*"` 无结果） |
| 经验载体 | 散落在 47 篇 ADR 的「背景/问题」章节、git commit message、Claude 会话历史 |
| 可检索性 | **无**。下次遇到同类问题无法定位"上次怎么解决的" |
| 可执行性 | **无**。约束写在文档里但没有检查点，违反无人知 |

### 1.2 本项目已经踩过并付出代价的坑（真实清单）

以下全部是**本轮及历史真实发生**的，不虚构：

| # | 坑 | 代价 | 根因 |
|---|---|---|---|
| 1 | `audit_logs.updated_at` 列不存在，RPO 锚点恒为 `none` | 备份演练的「RPO 一致」校验**形同虚设**，跑了很久才发现 | 写 SQL 未核对真实列名 |
| 2 | 仓储 `save()` 的 UPDATE 分支没捕获 `IntegrityError` | UniqueViolation 冒到 Worker 被当可重试 → **无限重试永不可能成功** | 异常翻译只在 insert 分支做 |
| 3 | 用 `begin_nested()` 包正常写入路径 | savepoint 释放破坏「审计失败→整体回滚」原子性 | 误以为 savepoint 是"更安全" |
| 4 | 只改 `status` 不改 `dispatch` | 撞 `ck_outbox_events_dispatch_status_consistent` 约束 | 不知道有该约束 |
| 5 | 合成容器头（`SYNTHETIC_*_CONTAINER_ONLY`）当样本 | 以为有真实样本，实际 zero payload | 未验证文件内容只看了扩展名 |
| 6 | 以为 RoboMimic `ph` 含图像 obs | Golden Path 设计偏差，需临时调整 | 未先探真实结构就设计 |
| 7 | E2E CI 硬编码 `passed===4 && skipped===1` | 新增 spec 后 CI 失败 | 计数写死在断言里 |
| 8 | mapper 计数断言 16 → 新增 mapper 后变 17 | CI 失败 | 用魔法数字而非集合相等 |
| 9 | `UPLOADED_BY` 边有契约有 DB 约束但**无生产者** | Session 链路永远查不到数据 | 三类定义（契约/约束/代码）未对齐 |
| 10 | 血缘 `limit=20` 实际返回 22 条 | 预算被投影边吃穿 | 遍历时未把剩余预算传给内层 |
| 11 | 全局+Tailscale 双代理配置，只改一处 | 全网不可访问，排查很久 | 系统代理有多个作用域 |
| 12 | 生成产物 schema 手改后被 check.sh 覆盖 | 改了没用 | 生成物不得手改 |

**这些坑的共同特征**：① 都真实发生过；② 都能用一条可执行检查提前拦住；③ 目前都没有沉淀。

### 1.3 不做的后果

- 同一类错误反复犯（如「魔法数字断言」已经在 #7 #8 出现两次）
- 新人无法从文档学到"这个项目不能怎么做"
- 审计报告每轮都要重新发现同样的边界

## 二、记忆卡片规范（按用户模板落地）

用户给定模板作为**唯一权威格式**，逐字段落地：

```markdown
### [MEMORY_ID] | [TITLE]

- **类型与状态**：`REQ / DEC / SOP / INC / CHG / OPS` | 状态：`DRAFT / ACTIVE / SUPERSEDED / DEPRECATED`
- **版本与血缘**：当前版本 `vX.Y` | 替代旧版 `<OLD_ID 或 无>` | 生效时间 `<YYYY-MM-DD>`
- **适用范围**：项目 `<PRJ_ID>` | 环节 `<STAGE>` | 批次/资产 `<BATCH/ASSET>` | 密级 `<SENSITIVITY>`
- **核心结论（1-3 句话说清是什么、定什么）**：
- **关键依据与细节（数据、实验、试采或排障事实）**：
- **影响与后续动作（对工期、成本、质量、SOP、脚本的影响及责任人/截止时间）**：
```

### 2.1 类型定义（6 类，各司其职）

| 类型 | 含义 | 本项目示例 | 谁该读 |
|---|---|---|---|
| **REQ** | 需求/验收口径 | "METADATA_ONLY 不等于训练就绪" | 产品、验收人 |
| **DEC** | 决策（含被否决方案） | "Adapter 分级用独立枚举而非改现有" | 架构、实施人 |
| **SOP** | 标准操作步骤 | "备份恢复演练 7 个不变量" | 运维、值班 |
| **INC** | 事故/缺陷复盘 | "UPDATE 分支漏捕获 IntegrityError" | 全体 |
| **CHG** | 变更记录（含风险） | "迁移 0072 归正 outbox 历史行" | 实施人、审计 |
| **OPS** | 运维参数/门禁 | "RTO 实测 10s / RPO 至备份时点" | 运维、SRE |

### 2.2 状态机（防止"过期记忆被当现行约束"）

```
DRAFT ──确认──> ACTIVE ──被取代──> SUPERSEDED
                  │
                  └──不再适用──> DEPRECATED
```

**硬规则**：
- 只有 `ACTIVE` 可被当作约束引用
- `SUPERSEDED` 必须指向 `替代旧版` 字段（谁是新的）
- `DEPRECATED` 必须写明**为什么不再适用**（否则下一个人不知道该不该信）

### 2.3 ID 命名（可检索、可排序、不撞车）

```
MEM-<类型>-<序号>-<短标题>
例：MEM-INC-001-update-branch-missing-integrity-error
    MEM-DEC-003-adapter-capability-levels
    MEM-OPS-002-rpo-rto-baseline
```

**规则**：
- 类型段用 2.1 的 6 类之一
- 序号三位、按创建递增，**不复用**（删了也留空号）
- 短标题用小写连字符，不超过 6 词

## 三、目录结构与分层

### 3.1 物理结构（文件为权威源）

```
docs/memory/
├── README.md                    # 使用说明 + 索引入口
├── MEMORY_INDEX.md              # 全量索引（自动生成，勿手改）
├── incidents/                   # INC 事故复盘
│   ├── MEM-INC-001-...md
│   └── ...
├── decisions/                   # DEC 决策
├── requirements/                # REQ 需求口径
├── sop/                         # SOP 操作流程
├── changes/                     # CHG 变更记录
├── ops/                         # OPS 运维参数
└── templates/
    └── memory-card.md           # 单卡片模板（复制即用）
```

### 3.2 为什么按类型分目录而不是按时间

- 按时间：找"上次那个坑"要翻全部
- 按类型：`INC` 只有事故，语义收敛，检索面小
- **代价**：跨类型关联需靠索引（3.3 解决）

### 3.3 索引与检索

| 层 | 机制 | 用途 |
|---|---|---|
| **权威源** | `docs/memory/**/*.md`（git 管理） | review / diff / 随分支演进 |
| **本地索引** | `MEMORY_INDEX.md`（脚本生成） | 快速浏览全量 |
| **语义检索** | OpenViking（跨会话召回） | "上次那个 UniqueViolation 怎么修的" |
| **强制检索** | `scripts/check_memory.py`（CI） | 违反 ACTIVE 约束时失败 |

### 3.4 与 OpenViking 的关系（关键设计）

```
文件（权威、可 review、可 diff）
   ↓ add_resource 导入
OpenViking（语义检索、跨会话召回）
   ↑ remember（仅用于即时决策，会被自动提取覆盖）
```

**规则**：
- **文件是唯一真相源**。OpenViking 只是索引，冲突时以文件为准
- 新增/修改记忆 → 先改文件 → 再导入 OpenViking
- **禁止**只在 OpenViking 里 remember 而不落文件（会变成不可 review 的暗知识）

## 四、核心机制：从"记录"到"约束"

### 4.1 三类可执行化路径（这是本系统的价值核心）

单纯记录 = 又一个无人读的文档。记忆必须**能拦住错误**：

| 记忆类型 | 可执行化方式 | 例子 |
|---|---|---|
| **INC**（事故） | 转成**回归测试** | #2 UniqueViolation → `test_content_duplicate_is_tombstoned_not_failed` |
| **DEC**（决策） | 转成**架构测试/CI 检查** | "不新建顶层模块" → 目录结构检查脚本 |
| **SOP**（流程） | 转成**可执行脚本** | 备份演练 → `backup-restore-drill.sh` + 11 条结构校验 |
| **OPS**（参数） | 转成**配置 + 监控阈值** | RTO/RPO 基线 → 演练脚本输出断言 |
| **REQ**（口径） | 转成**验收断言** | "METADATA_ONLY 不等于 frame" → 状态枚举强制区分 |
| **CHG**（变更） | 转成**迁移 + 回滚验证** | 迁移 0072 → 真实 PG upgrade/downgrade 测试 |

**每张记忆卡片必须有 `check_ref` 字段**（见 §4.2），指向拦它的测试/脚本/CI 步骤。**没有 check_ref 的 INC 卡片不允许 ACTIVE**——否则它只是日记。

### 4.2 卡片扩展字段（在用户模板基础上增加）

用户模板是 7 个字段（类型状态/版本血缘/适用范围/核心结论/关键依据/影响动作）。为支撑"可执行"，增加 3 个工程字段：

| 新增字段 | 必填性 | 用途 |
|---|---|---|
| `check_ref` | INC/DEC/SOP **必填** | 指向拦截该问题的测试/脚本路径 |
| `recurrence` | 选填 | 复发次数（>1 说明上一轮记忆没生效） |
| `tags` | 必填 | 检索标签（领域/技术栈/阶段） |

**为什么加这三个**：
- `check_ref`：把"记住"变成"拦住"，这是记忆系统区别于文档的关键
- `recurrence`：识别"反复踩同一个坑"，触发根因升级
- `tags`：跨类型关联的唯一手段（因为按类型分目录）

## 五、生命周期：什么进、什么不进、什么时候退

### 5.1 入库门槛（防止记忆库变成噪音池）

**必须入库**（任一满足）：
1. 造成过 ≥30 分钟排查时间
2. 造成过 CI 失败 / 数据错误 / 线上异常
3. 是**违反直觉**的（"看起来该这样，实际不能"）
4. 是**不可逆操作**的前置条件（删除/迁移/发布）
5. 是**跨模块**的隐性契约（如"生成物不得手改"）

**不入库**：
- 一次性拼写错误（无学习价值）
- 已在代码注释里说清且不会复发的小事
- 纯个人偏好（除非影响团队）

### 5.2 退出机制（防止记忆库腐烂）

| 触发 | 动作 |
|---|---|
| 约束已固化到 CI/测试，且 6 个月未复发 | 可降级 `DEPRECATED`（但 check_ref 保留） |
| 技术栈变更导致约束不再适用 | 改 `DEPRECATED` + 写原因 + 指向新卡片 |
| 被发现是错的 | 改 `SUPERSEDED` + 指向纠正卡片 |
| 同一个坑复发 ≥2 次 | **升级为 INC + 强制加 CI 检查**（现有 check 没生效） |

### 5.3 定期复审

| 频率 | 动作 |
|---|---|
| 每次发版前 | 跑 `check_memory.py`，确认所有 ACTIVE 卡片 check_ref 有效 |
| 每月 | 复审 `recurrence > 1` 的卡片，判断是否需要更强约束 |
| 每季度 | 复审 `DEPRECATED`，可归档 |

## 六、检索设计（"怎么找到上次那个坑"）

### 6.1 三种检索路径

| 场景 | 路径 | 工具 |
|---|---|---|
| "我记得有个类似问题" | 语义检索 | OpenViking `search` |
| "改这块要注意什么" | 按 tags/环节 | `MEMORY_INDEX.md` 分组 |
| "这个报错见过吗" | 精确匹配错误码/消息 | `grep docs/memory/` |

### 6.2 索引生成

`scripts/build_memory_index.py`：
- 扫描 `docs/memory/**/*.md`
- 提取 ID/类型/状态/标题/tags/check_ref
- 生成 `MEMORY_INDEX.md`：按类型分组 + 按 tags 交叉索引 + 失效卡片单独列出
- **CI 校验索引与卡片一致**（防手改漂移）

### 6.3 与开发流程的集成点

| 时机 | 动作 |
|---|---|
| 开工前 | 按模块/tags 检索相关记忆（尤其 DEC/REQ） |
| 遇到报错 | `grep docs/memory/` 查是否已知 |
| 修复问题 | 判断是否达入库门槛 → 建卡 → 加 check_ref |
| PR 提交 | PR 模板增加「是否新增/更新记忆卡片」勾选 |
| CI | `check_memory.py` 校验格式、索引、check_ref 有效性 |

## 七、与现有体系的关系（不重复建设）

| 现有资产 | 与记忆系统的边界 |
|---|---|
| `docs/adr/` | ADR 是**决策的完整论证**；记忆卡 DEC 是**决策的浓缩 + 可检索入口**，`check_ref` 指向 ADR + 测试。**不复制 ADR 正文**，只引用 |
| `docs/roadmap/*/`（蓝图/审计） | 蓝图是**规划**，审计是**时点事实**；记忆是**跨时点的教训**。审计报告发现的问题 → 抽取为 INC 卡片 |
| `docs/testing/evidence/` | 证据是**某次验证的产物**；记忆是**从那次的教训** |
| `CLAUDE.md` / `AGENTS.md` | 是**给 Agent 的硬约束**；记忆卡是**约束的由来与证据**。二者互相引用 |
| `docs/architecture/` | 设计说明；记忆卡引用它而非重写 |

**一条硬规则：记忆卡不复述已有文档，只写"新增的教训 + 指向既有证据的引用"。**

## 十、诚实边界

- 本设计**不解决**「记得但不执行」的根因——那需要文化而非工具；本系统能做的是**降低检索成本 + 提高违反成本**（CI 拦截）。
- `check_ref` 只能覆盖**可自动化**的约束；「沟通类教训」（如"评审要先对齐口径"）无法自动化，只能靠 `recurrence` 追踪。
- 首批 12 条来自**本轮及历史真实事实**，不含推测。后续新增需按 §5.1 门槛。
