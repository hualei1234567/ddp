## 6. 修掉的断点

### 6.1 已修复：数据源导入 Worker 的系统执行身份违反外键

- 位置：`backend/app/workers/datasources.py`
- 缺陷：Worker 用 `ProjectScope(project_id, actor_id=project_id)` 执行导入。`data_source_imports.updated_by`
  与 `raw_assets.created_by` 都有 FK → `users.id`，第一次状态推进即
  `FOREIGN KEY constraint failed`。线上表现是「导入任务反复重试、事件耗尽进死信」。
  该缺陷与 `ingestion_jobs` Worker 修复前的缺陷同源（后者已在代码中注释该坑）。
- 证据（修复前探针）：`IntegrityError: (sqlite3.IntegrityError) FOREIGN KEY constraint failed
  [SQL: UPDATE data_source_imports SET ... updated_by=? ...]`
- 修复：新增 `_import_creator()`，从导入任务行取 `created_by` 作为系统执行身份；
  重试分支回滚后重新解析。语义：系统代导入发起人执行。
- 回归：`tests/workers/test_datasource_import_worker.py` 断言 `created_by == updated_by == 提交人`、
  `updated_by != project_id`，并验证事件发布、审计 `create/start/succeed`、RawAsset `VALID`、重复投递 `IDLE`。

### 6.2 已补齐（2026-11-17，分支 `worktree-episode-manifest`）：Canonical Manifest 生成与自动就绪

> 本节保留原始缺陷记录（历史事实）；补齐方案、判定规则与实测结果见 **§12**。

- 现象：`POST /data-source-imports/{id}/episodes` 物化出的 Episode 状态为 `PENDING`；
  进入 `READY` 需要 `POST /episodes/{id}/actions/ready` 提交 Manifest，而平台内**没有任何组件**
  从导入产物生成 Canonical Manifest（`data-platform/` 无 manifest 能力，Worker 只做导入）。
  这会让「导入 → Episode → 标注 → 数据集」在人工介入前完全中断。
- 本轮处理：e2e 以**显式 ready 动作**补位，Manifest 的每个 stream（object_key/sha256/size_bytes）
  都取自 `GET /raw-assets/{id}` 的真实落库事实，`quality` 如实为 `NOT_CHECKED`；测试文档与代码
  均标注「代为执行缺失的 canonicalization 步骤」。
- 为何本轮不改：需要产品决策（Manifest 的 `streams/time_alignment` 对原始视频的语义、是否需要
  转码生成 Canonical 文件、`frame_count` 从何而来）以及契约层确认，不能由 QA 单方面定义；擅自
  自动置 `READY` 会把未校验数据送进标注与数据集准入。
- 影响：`PARTIAL`（链路可人工推进，非自动）。

### 6.3 未修复：血缘图不含数据源 / 导入任务节点

- 现象：`LineageNodeType` 只有 `RAW_ASSET / UPLOAD_SESSION / COLLECTION_TASK / COLLECTION_BATCH /
  INGESTION_JOB / EPISODE / QUALITY_RUN / ANNOTATION / DATASET_VERSION / TRAINING_RUN`。
- 影响：`RawAsset → 数据源` 只能靠 `raw_metadata` JSON 反查（见 §4）。
- 为何本轮不改：新增节点类型要同步 `lineage_node_refs.node_type` 的 CHECK 约束（迁移）、
  `LineageNodeType` 枚举与 OpenAPI 契约；本任务明确禁止修改 `packages/contracts/`，且需要 ADR。

### 6.4 观察项（不阻断）

- `backend/app/api/v1/datasource_routes.py` 的 `__all__` 声明在最后一条路由之前（位置问题，无功能影响）。
- 导入链路的 Episode `frame_count` 为 0（未解码视频，链路无从得知帧数）；Manifest 如实记 0，不猜测。

### 12.2 判定规则（哪些自动就绪、哪些保持 PENDING）

自动置 READY 必须**同时**满足；任一不满足即登记一条可读原因并保持 `PENDING`：

| 条件 | 不满足时的拒绝码 |
|---|---|
| 至少一条机位流，且每条流的机位、object_key、sha256、大小、格式齐备可用 | `STREAMS_MISSING` / `STREAM_INCOMPLETE` |
| 关联记录里的 Hash/大小快照与当前资产一致 | `STREAM_SNAPSHOT_MISMATCH` |
| `time_base` 通过既有校验，且 `sync_status` 不属于 `{UNVERIFIED, FAILED}` | `TIME_BASE_INVALID` / `TIME_SYNC_UNVERIFIED` |
| **多机位** Episode 必须有标定快照 | `CALIBRATION_MISSING` |
| Episode 时长 > 0 | `DURATION_UNKNOWN` |
| 每一路机位都声明了有效 `source_fps`，且各机位一致 | `FRAME_RATE_UNKNOWN` / `FRAME_RATE_INCONSISTENT` |
| 由「时长 × 帧率」推出的帧数 > 0 | `FRAME_COUNT_UNDETERMINED` |

需要产品确认的两条口径（已按下列方式实现，**不是**随手放宽）：

1. **帧数**＝`Episode 时长（纳秒，权威）× 机位声明的 source_fps`，不跨机位求和
   （求和会把同一时间轴的帧重复计数）。平台不解码视频，因此只承认**声明的帧率**；
   声明缺失即判为不可确定，不猜。该值同时写入 Manifest 的 `frame_count`。
2. **标定**：多机位缺失标定 → 拒绝（没有机位间几何关系，多路流无法构成可融合
   样本）；单机位缺失标定 → **不阻塞但显式留痕**（notice
   `SINGLE_STREAM_CALIBRATION_ABSENT` 写进审计）。这与既有决策一致：能否建
   Episode 只看字段结构（`validate_calibration_snapshot`），标定是否可接受由数据集
   准入判断（`CALIBRATION_MISSING` / `allow_missing_calibration`），不在 Episode 上
   伪造标定快照。

### 12.3 「导入成功」与「Episode 未就绪」是两种结果

- 导入任务的结论不受影响（`SUCCEEDED` 照旧）；
- 自动就绪被拒只写 `episodes.readiness_blockers` + 审计事件
  `ingestion.episode.readiness-blocked`（留痕类，无消费者）；
- 未被就绪阻塞的写路径（状态动作、修订、质检结论）保持原样；
- **未**启用「就绪失败即导入失败」，也**未**把原因塞进 `failure_reason`
  （后者已被 `mark_failed` / `reject` / `invalidate` / 采集失败占用，混用会让
  正常流水线里的 Episode 被失败统计误计，且真实失败原因会覆盖就绪原因）。

### 12.4 幂等与并发

- 非 `PENDING` 的 Episode 直接 `SKIPPED`（已就绪不重写，已驳回不复活）；
- 重复物化：Episode 已存在时**重新判一次**就绪（数据补齐后可以真的就绪），
  已就绪的仍 `SKIPPED`，版本号不变（用例断言过）；
- 并发：两段写入（`PENDING → PROCESSING → READY`，DB 触发器只登记该白名单）中
  第二段若因乐观锁失败，显式 `rollback` 本次半成品并返回 `SKIPPED`，
  避免把 Episode 留在没有出口的 `PROCESSING`。

### 12.5 与任务书的偏差（如实记录）

任务书写「导入 Worker 在创建 Episode 后自动就绪」，但**导入 Worker
（`DataSourceImportWorker`）不创建 Episode**：它只把文件落成 `RawAsset` +
媒体资产。Episode 的创建点是 `ImportEpisodeMaterializer`（`POST
/data-source-imports/{id}/episodes`，`workers/ingestion_jobs.py` 的
`SEGMENT_EPISODE` 目前显式返回"不支持"）。因此自动就绪接在**物化器**上——那是
导入链路唯一的 canonicalization 入口，HTTP 与任何未来调用方都走这一条路径。
若要「导入完成即自动物化」，需要产品确认（是否需要人工指定 `scene_labels`、
是否需要新的 `datasource.import.succeeded → 物化` 事件链），本次未擅自扩大范围。
