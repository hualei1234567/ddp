## 四、一个必须记录的实测陷阱：`n_live_tup` 不可信

**103 张表中有 83 张的 `pg_stat_user_tables.n_live_tup` 与精确 `COUNT(*)` 严重不符。**

最刺眼的两张：

| 表 | `n_live_tup` | 精确 `COUNT(*)` | 偏差 |
|---|---:|---:|---:|
| `outbox_events` | **35** | **12,518** | **358 倍** |
| `audit_logs` | **39** | **12,481** | **320 倍** |

**根因（已定位到事实层面）**：`ddp-postgres` 容器于
**2026-11-23T05:25:03Z 重启**（`docker inspect` 证实）。
PostgreSQL 的统计信息存放在**共享内存**中，容器重启即清零，
而表数据在磁盘上存活。

**关键证据**：`outbox_events` 中 `created_at >= 2026-11-23 05:25:03+00` 的行
恰好是 **35** 行，与 `n_live_tup=35` **完全相等**——精确等于重启后新增的行数。
`audit_logs` 同样是 **39**。

**这也解释了 `pg_stat_database.stats_reset` 为空却统计失真**：
`stats_reset` 只记录**显式 `pg_stat_reset()` 调用**，容器重启不写该字段，
所以"stats_reset 为空"**不能**用作统计新鲜的证据。

> **这直接影响既有结论**：`docs/testing/evidence/2026-11-26-index-audit/README.md`
> 写着「`audit_logs` 39 行、`idempotency_records` 0 行……都建在小表上」——
> 当时的 `audit_logs` **真实行数是 12,481 行**，不是 39 行。
> 该报告关于"**没有可删索引**"的核心结论**不受影响**（因为零使用索引的判定
> 依赖 `idx_scan` 样本量，而 `idx_scan` 累计 3,619,952 次，样本充分），
> 但它**低估了表的规模**，其"小表豁免"的论证基础需要修正。
> **本审计已用精确 `COUNT(*)` 取代 `n_live_tup`**。

### 索引审计结论是否被推翻？

**没有。** 但补充一条更重要的结论：索引审计当时判定
`audit_logs` 是"小表"因而需要"表长大后复查"——**它已经长大了**（12,481 行）。
本审计的证据 JSON 中包含每张表的精确行数，未来复查应直接用它。

| 阈值 | 数值 | 作用 |
|---|---|---|

| **分区评估触发（体积）** | **50 GiB**（含索引） | 单表体积达此值 → 启动分区评估 |

### 5.2 依据：写入 TPS × 保留天数 = 预期行数

写入容量实测来自 `docs/testing/evidence/2026-11-26-write-path-capacity/README.md`：

| 并发 | 样本 | p95 | TPS |
|---|---:|---:|---:|
| 1 | 150 | 1.96ms | 698 |
| 4 | 600 | 2.44ms | **2,443** |
| 16 | 2,400 | 8.54ms | **2,548**（饱和） |

该证据给出的部署建议：**单实例承接 1,200 TPS**（4 并发档留 50% 余量）。

**据此推算 5000 万行何时被触及**：

| 场景 | 写入速率 | 触及 5000 万行所需时间 |
|---|---:|---:|
| 单实例建议容量 | 1,200 行/秒 | 41,667 秒 = **约 11.6 小时** |
| 单机实测饱和 | 2,548 行/秒 | 19,623 秒 = **约 5.5 小时** |

> **这是阈值的核心含义**：5000 万行**不是遥不可及的数字**。
> 平台一旦承认真实业务流量并跑满单实例容量，
> `outbox_events` / `audit_logs` 会在**半天之内**触及行数阈值。
> 换言之——**分区是"业务起量后立刻要面对"的问题，而不是" someday 的问题"**；
> 但**今天**（实测 0.0007 行/秒）它离触发还差 **170 万倍**。

### 5.4 依据：归档阈值的代码事实

`backend/app/workers/maintenance.py` 的 `sweep_once()` 是**单条无分批 DELETE**：

```python
archived = session.execute(
    delete(OutboxModel).where(
        OutboxModel.status.in_(_ARCHIVABLE_STATUSES),
        OutboxModel.created_at < event_cutoff,
    )
).rowcount
```

按实测每行成本换算单次 DELETE 的 WAL 量级：

| 表 | 归档行数 | 单条 DELETE 产生 WAL |
|---|---:|---:|
| `outbox_events` | 1,000,000 | ≈ 0.52 GiB |
| `outbox_events` | **10,000,000** | **≈ 5.22 GiB** |
| `audit_logs` | **10,000,000** | **≈ 4.96 GiB** |

**分批删除**或**分区整体摘除（DROP 分区）**。

## 六、归档策略建议（**复用现有能力，不另起平行实现**）

### 6.1 现状：已有机制覆盖了唯一需要归档的表

`backend/app/workers/maintenance.py` 的 `MaintenanceWorker.sweep_once()` 已实现：

- **归档**：`outbox_events` 中 `status IN ('PUBLISHED','RECORDED')` 且
  `created_at < now() - outbox_retention_days`（默认 **30 天**）的行被删除。
- **不删**：`PENDING`（还在等消费者）与 `FAILED`（死信需人工处理）——**这是对的**。
- **清扫**：`idempotency_records` 中 `expires_at < now()` 的行被删除。

**实测运行状态**：`ddp-maintenance-worker` 容器运行中，
最近 200 次"清扫完成"日志**全部成功**、0 失败；当前
`outbox_events` 中**超过 30 天的行数为 0**——**保留策略正在生效**。

> 历史插曲：2026-11-23 容器重启期间曾有一批"清扫失败"（连接被拒），
> 属环境问题，重启后已恢复。

### 6.2 建议：**当前不动**，仅在触发线上做两件事

| 表 | 当前建议 | 触发后的动作 |
|---|---|---|
| `outbox_events` | **维持现状**（30 天保留 + 现有清扫） | > 1000 万行：把单条 DELETE 改**分批**（每批 10 万行）或改为**分区整体摘除** |
| `idempotency_records` | **维持现状**（`expires_at` 自过期） | > 1000 万行：同上加分批 |
| `audit_logs` | **维持现状** | > 1000 万行：**必须先解决 append-only 语义**——`trg_audit_logs_no_delete` 会拒绝 DELETE。需与安全/合规方确认"审计日志可否按期归档"，再改触发器或改走分区归档（分区可用 `DETACH` + 归档文件，语义上比 DELETE 更干净） |
| `episodes` | **不归档**（业务主数据） | > 1,690 万行 / 50 GiB：评估按 `created_at` 月度分区，**归档用 DETACH 而非 DELETE** |
| 其余表 | **不归档**（小且多为业务主数据/派生数据） | 达 1000 万行再单独评估 |

### 6.3 明确不做的事

- **不新建归档表/归档 schema**：现有 `maintenance.py` 已够用；另起一套会造成
  两份保留策略互相打架（这正是 `MEM-INC-012`「enum 多表 CHECK 约束」、
  `MEM-INC-018`「并行 PR 迁移链冲突」这类教训的同类风险）。
- **不新建定时任务**：归档已挂在维护 worker 的主循环里。
- **不改 `audit_logs` 的 append-only 触发器**：那是安全语义，不是性能问题。

## 七、复现方式

```bash
# 1) dry-run（默认，不连库、不执行任何查询）
python3 scripts/db/table_growth_audit.py --dsn postgresql+psycopg://ddp:ddp@localhost:55432/ddp

# 2) 真实执行（只读 SELECT）
python3 scripts/db/table_growth_audit.py \
  --dsn postgresql+psycopg://ddp:ddp@localhost:55432/ddp \
  --execute --format json --out table-growth-audit.json
```

**只读保证（三层）**：

1. **代码层**：脚本内所有 SQL 均为 `SELECT`/`WITH`，无任何 DDL/DML；
2. **运行层**：每条 SQL 执行前经 `assert_select_only()` 断言——
   前缀必须是 `SELECT`/`WITH`，且经**词边界**关键字扫描
   （`INSERT`/`UPDATE`/`DELETE`/`DDL`/`VACUUM`/…），
   **CTE 里藏的写操作同样会被抓住**；
3. **目标层**：默认只允许连 loopback（`localhost`/`127.0.0.1`/`::1`），
   非 loopback 必须显式 `--allow-non-loopback`（该开关**只放开读**）。

**DSN 脱敏**：报告与终端输出中的口令一律替换为 `***`（复用
`scripts/perf/core.py` 的 `mask_dsn`），主机与库名保留以便核对目标。

## 八、诚实边界

- **数据窗口只有 10 天**（2026-11-14 ~ 11-26），且其中 3 天是压测尖峰。
  有机基线只由 **7 个日样本**支撑，统计意义有限——**这是"暂不需要"结论
  最重要的不确定性来源**。若真实业务流量特征与压测不同，基线会变。
- **单机单副本 PG**：未验证主从/多副本下的统计与容量行为。
- **`n_live_tup` 不可信**意味着膨胀率（`n_dead_tup`）同样不可信——
  `outbox_events` 的 62 个死元组只是**重启后**的统计，不代表全量。
  本审计因此**不基于膨胀率下任何结论**（当前也无膨胀迹象）。
- **未做 `EXPLAIN`**：分区收益应基于真实查询计划评估，本次未验证
  "哪些查询会因分区受益"——**这是分区评估阶段（触发后）的工作，不是现在**。
- **未覆盖非 `public` schema**：生产库还残留 3 个历史测试 schema
  （`ddp_v51017_*` 95 张表 / 5.0 MiB、`ddp_dbg_*` 95 张表 / 3.8 MiB、
  `probe_rename` 1 张表），本审计按约定**只扫 `public`**。
  这些残留合计约 8.8 MiB，占全库 4%，**不改变结论**，但值得单独清理
  （清理属 DDL，需另行审批）。
- **本审计不构成实施分区/归档的批准**：它只提供判定与阈值。
  触发阈值后需走 ADR + 迁移 + 回滚评审。
