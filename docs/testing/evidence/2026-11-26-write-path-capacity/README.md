# 写路径容量探测证据（审计 R1）

## 审计缺口

> 「写路径零压测：标注提交、任务创建、导出触发等写操作的真实延迟与锁竞争完全未知，无法回答扩容问题。」

## 探测对象与口径

**测什么**：本项目每个领域写操作在同一事务里都写「审计行 + outbox 事件」——
这是所有写路径的**公共事务骨架**。并发写这两张表能回答：可持续写入 TPS、
p95 提交延迟、死锁/锁等待。

**不测什么**：端到端 HTTP 写接口的业务延迟（需先造任务/批次/分配/提交完整前置
数据，且会把业务校验耗时混进容量数字）。业务链路压测留后续任务。

## 实测结果（本机 PG 16.16，隔离临时库，每次写入 = 审计 + outbox 双写）

| 并发 worker | 样本 | 错误 | p50 | p95 | p99 | TPS | 死锁 | 锁等待 |
|---|---|---|---|---|---|---|---|---|
| 1 | 150 | 0 | 1.27ms | 1.96ms | 5.69ms | **698** | 0 | 0 |
| 4 | 600 | 0 | 1.29ms | 2.44ms | 5.26ms | **2,443** | 0 | 0 |
| 16 | 2400 | 0 | 5.30ms | 8.54ms | 17.59ms | **2,548** | 0 | 0 |

**关键观察**：
1. **1→4 并发扩展良好**：TPS 提升 3.5 倍，p95 几乎不变（1.96→2.44ms）
2. **4→16 已饱和**：TPS 只提升 1.04 倍，p95 涨到 8.54ms（4.4 倍）——说明 4 并发后
   瓶颈从「单连接串行」转为「PG 侧写入争用」，继续加连接只增延迟不增吞吐
3. **零死锁、零锁等待**：写事务骨架无交叉加锁，这是「审计+outbox 同表顺序写入」
   设计带来的直接好处

## 导出的容量模型

### 连接池规模

实测饱和点在 4–8 并发写事务之间。按「每 worker 持 1 连接」计：

| 部署形态 | 建议 DB 连接池 | 依据 |
|---|---|---|
| 单 API 实例 | `pool_size=8, max_overflow=8`（上限 16） | 超过 16 只增延迟；留 2 倍余量应对突发 |
| 多 API 实例（N 个） | 每实例 `pool_size = min(8, 100/N - 预留)` | PG `max_connections=100`，需为 worker/迁移/人工连接预留，**总连接数不得超过 80** |
| worker 进程（13 个服务） | 每 worker `pool_size=2` | worker 以批处理为主，不需要宽池 |

**红线**：所有进程连接总和 ≤ 80（`max_connections=100` 留 20% 给运维/迁移/监控）。
当前 compose 有 13 个服务，若全部起满且各 pool_size=8，需要 104 > 100 → **会打满**。
这是必须按上表收敛配置的具体原因（不是理论担忧）。

### 容量估算公式

```
可持续写入 TPS（单机）≈ 2,500（本机实测饱和值）
单实例建议承接 TPS  ≈ 1,200（在 p95 < 5ms 区间内留 50% 余量，即 4 并发档）
期望业务写入 QPS    → 所需 API 实例数 = ceil(QPS / 1,200)
```

### 与业务量的对照

当前生产库最大表 240 行，实际写入 QPS < 1。**当前配置有 1000 倍以上余量**。
真正需要关注容量是在：批量导入（万级 Episode）、批量回流受理、导出任务集中触发
这三个场景，它们会瞬间产生数千次写。

## 复现方式

```bash
# dry-run（默认，不写任何东西）
python scripts/perf/write_path_probe.py --dsn postgresql+psycopg://ddp:ddp@localhost:55432/postgres

# 真实执行（自动建临时库 → 跑迁移 → 打完即删）
python scripts/perf/write_path_probe.py \
  --dsn postgresql+psycopg://ddp:ddp@localhost:55432/postgres \
  --execute --workers 1,4,16 --iterations 150 --out /tmp/write-probe.json
```

原始数据：`write-probe-raw.json`

## 安全护栏（硬编码）

1. **只允许本机回环 PG**，非 loopback 直接拒绝
2. 建库连接点必须白名单（`postgres` / `ddp`）；临时库名必须以 `ddp_perf_write_` 开头
3. **默认 dry-run**，必须显式 `--execute`
4. 并发上限 32（生产写保护）
5. 只写临时库，结束 `DROP DATABASE ... WITH (FORCE)`

## 诚实边界

- 单机 PG，未验证多副本/主从切换下的表现
- 未覆盖：真实业务校验耗时、跨表事务（如提交时同时改任务状态与分配状态）、大字段写入
- 未做长稳（>10 分钟）观测：连接泄漏与内存增长未验证
- 数据量为空库（写入目标表无历史数据），有数据时索引维护成本会更高，TPS 会下降
