## 5. 「Dataset → 数据源」为什么是两段组合而不是一次遍历

跳数账：`DATASET_VERSION ← EPISODE ← RAW_ASSET ← DATA_SOURCE_IMPORT ← DATA_SOURCE` 共 **4 跳**。
逐节点血缘端点 `depth` 上限 5、`limit` 上限 100，理论上够。

实测不够，原因是**数据形态**而非实现：

- 该链路 3 个资产在导入历史里各挂了 **29~34 条** `data_source_media_assets` 行（同一份数据被反复导入/重导）；
- 反向第 3 层展开时，每层一跳就是 80+ 条同名 `DATA_SOURCE_IMPORT → RAW_ASSET` 边；
- 100 的边预算在第 3 层被吃满，第 4 层的 `DATA_SOURCE` 边被挤掉。

E2E 的处置（**没有放宽实现、没有偷偷提高上限**）：

1. 如实记录单次遍历只能到 `DATA_SOURCE_IMPORT`（`single_traversal_edges=100`）；
2. 用**两段组合**完成验证：`版本 --反向 2 跳--> 资产` + `资产 --反向 2 跳--> 数据源`，两段都真实执行、真实断言；
3. 额外证明 graph 端点以**资产为根**、`direction=IN`、`depth=2` 可直达 `DATA_SOURCE`（`graph_asset_root_node_types` 含 `DATA_SOURCE`）。

结论：**能力齐备**（4 条路径都通），**单次调用从 DatasetVersion 到数据源在重复导入数据下会被边预算截断**——这是可解释的截断（`next_cursor` 非空），不是缺陷，但应在能力矩阵里如实标注为「需两段组合或更大边预算」。

## 6. 「Dataset → Session」为什么 UNVERIFIABLE

两层结论分开，不合并：

**机制层 PASS。** 修掉了一个真缺陷（见 §7.1）后，项目内 5 个带上传会话的资产，`RAW_ASSET --UPLOADED_BY--> UPLOAD_SESSION` 投影边都真实返回，`metadata.derived=true`，边 id 确定性（两次查询同一 id）。

**链路层无数据。** 被验版本的 4 个 Episode 全都没有 `capture_session_id`（`0/4`），3 个 RawAsset 也都没有任何 `raw_asset_links.upload_session_id`（`0/3`）。库里共 28 条会话链接，但**全部落在手工上传资产上**，没有一个进入过 Episode / DatasetVersion：

```sql
-- 库内 28 条上传会话链接涉及的资产中，进入 Episode 的：0；进入 DatasetVersion 的：0
```

为什么：当前进入数据集的真实数据全部来自 **HF 导入链路**（`source_type=IMPORT`），这条链路不产生上传会话 / 采集会话；而带会话归属的数据是**手工上传/设备采集**路径产生的，该路径目前没有走到 Episode/数据集。这是**数据生产链条的缺口**，不是血缘查询的实现问题。

要闭环这一段，需要（按优先级）：

1. 让「采集会话 → 上传会话 → RawAsset → Episode」这条真实业务链路跑一遍并进入一个 DatasetVersion（`tests/api/test_capture_session_upload_linkage.py` 已证明采集会话→资产段可用，缺的是走到 Episode/数据集）；
2. 或者，明确产品口径：数据集的准入是否允许/要求带采集会话归属的数据；若允许纯导入数据入集，则「Dataset → Session」对本类数据**本就不适用**，应作为口径写进能力矩阵而不是当作缺口。

## 7. 修掉的真实缺陷（3 个）

### 7.1 `UPLOADED_BY`（RawAsset → UploadSession）有契约、有约束、**没有生产者**

- 现象：`LineageRelation.UPLOADED_BY` 在领域枚举、`data_lineage_edges` 的 CHECK 约束、OpenAPI `LineageRelation` 枚举、`docs/architecture/阶段2-Episode血缘与API摘要-v1.md` §8.4 里都存在，方向定义为「`RAW_ASSET → UPLOAD_SESSION`，资产由会话登记」；但**全仓没有任何代码写这条边**（`grep UPLOADED_BY` 在 `app/` 下只命中枚举与约束定义）。结果：任何「这条数据是从哪个采集/上传会话来的」查询都必然为空。
- 判定依据：这不是"数据没到"，是**能力缺失**——即使造出带会话的数据，血缘也查不到。
- 修法（与既有数据源链同一套取舍，**不加迁移、不写持久化边**）：
  - 新增 `backend/app/application/episodes/session_provenance.py`：`SessionProvenanceResolver` 把 `raw_asset_links`（`link_type=UPLOAD_SESSION` 且未 `REVOKED`）投影成 `RAW_ASSET --UPLOADED_BY--> UPLOAD_SESSION` 边；边 id 由端点 `uuid5` 确定性派生，`created_by/created_at` 取链接行本身，`metadata.derived=true`；`capture_session_id` 经 `metadata` 透出（节点类型集合里没有 `CAPTURE_SESSION`，新增要迁移 + 契约变更，不在本 PR 范围）。
  - 新增 `backend/app/infrastructure/repositories/session_provenance.py`：只读 SQL 适配器，所有 JOIN 都带 `project_id`，`REVOKED` 链接不产边。
  - 接入 `LineageService`（逐节点血缘）与 `LineageGraphService`（图查询）的 BFS 投影展开：`RAW_ASSET` 正向 / `UPLOAD_SESSION` 反向。
  - `UPLOAD_SESSION` 加入 `PROJECTED_NODE_TYPES`：图查询以它为根之前，先用权威仓储确认归属，跨项目/不存在一律 **404**（不泄露存在性）。
- 回归测试：`backend/tests/api/test_lineage_session_projection_api.py`（7 条，见 §8）。
- 诚实边界：这是**读时投影**，覆盖历史数据与新增数据一视同仁；但它不改变"导入链路不产生上传会话"这个事实——所以本库的 Dataset→Session 仍然无数据可验（§6）。

### 7.2 逐节点血缘的 `limit` 被突破（返回条数超过 `limit`）

- 现象：`limit=20` 实测返回 **22 条**边。根因两处：
  1. `LineageService.trace` 只把**持久化边**计入 `limit`，投影边（数据源链）额外追加，不受预算约束；
  2. 达成预算后只 `break` 了内层"边循环"，外层"节点循环"仍会为后续每个前沿节点再塞一条边。
- 影响：客户端按 `limit` 分页/渲染会拿到超预期条数；更糟的是**超出部分被静默丢弃**，调用方无法区分"到头了"与"被截断"。
- 修法：投影边查询传剩余预算（`edges_so_far`），预算耗尽立刻终止本层并停止下钻（邻接不完整时不再扩层）。
- 回归测试：`test_node_lineage_limit_is_not_exceeded_by_projection_edges`（覆盖 `limit=1/3/5/20`）。

### 7.3 版本血缘端点丢弃了 `raw_asset_sources`（FR-040 的核心字段）

- 现象：`GET /projects/{p}/datasets/{d}/versions/{v}/lineage` 调用的是
  `LineageService.traverse()`——**只返回边**，把 `trace()` 已解析好的
  `raw_asset_sources` 直接丢掉。实测反向 2 跳返回 18 条边（覆盖 3 个 RawAsset），
  `raw_asset_sources` 却是 **0 条**；同一时刻 Episode / RawAsset / graph 三个端点
  都正常带回 3 条 `RESOLVED`。修复后该端点返回 **3 条 `RESOLVED`**。
- 影响：这正是 FR-040 的核心诉求——「从 Dataset 追问数据最初来源」。四个血缘端点
  里唯独版本血缘（追溯起点）拿不到来源结论，调用方只能自己从投影边 `metadata`
  反推 `data_source_id` / `import_id`，与契约
  （`LineageResponse.raw_asset_sources` 的语义说明）矛盾，也让 E2E 第 4 段
  无法只靠版本端点完成。
- 修法：改为调用 `trace()` 并用 `build_lineage_response(trace, direction)` 组装
  （与另外三个端点共用同一份 DTO 转换，不再各写一份）。
- 回归测试：`test_version_lineage_returns_raw_asset_sources`。

### 7.4 不是缺陷、但如实记录的观察

- **graph 端点硬上限 depth=3 到不了数据源**：从 DatasetVersion 到 DATA_SOURCE 需 4 跳，`MAX_GRAPH_DEPTH=3` 按设计追不到。这不是 bug（契约明写硬上限 3 且触顶给 `truncated`），但「用 graph 一次查全链」的预期不成立，必须用逐节点端点或组合查询。已在 E2E 第 5 段如实标注。
- **导入历史里的重复导入**（同一资产挂几十条媒体行）会显著放大边预算消耗。数据卫生问题，不在本 PR 修（清理历史导入需要产品/运维决策）。

## 10. 复现性

- 脚本**只读**：不写任何业务表、不新建项目/资产/边，重复执行得到相同结论（唯一变量是库里数据本身）。
- 链路发现用 SQL 从库内真实数据推导，不写死 ID（可用 `DDP_LINEAGE_PROJECT_ID` 锁定项目）。
- 断言基于「库内权威事实 vs 血缘 API 返回」的交叉核对，不是「API 返回非空即通过」。
- 单次运行（真实 PG + 真实 MinIO）约 10 秒。

## 11. 对 FR-040 状态的建议

**保持 PARTIAL**，但更新其 PARTIAL 的理由与剩余缺口（从"缺 E2E"改为"E2E 已跑，Dataset→Session 链路无真实数据"）。

1. 造出并跑通「采集会话 → 上传会话 → RawAsset → Episode → DatasetVersion」一条真实链路，使 §6 的链路层有数据、E2E 第 6 段转为 PASS；**或**
2. 产品/架构明确裁定「纯导入数据不要求 Session 归属」，则 FR-040 的验收口径应收窄为「Dataset → RawAsset → 数据源」，此时现有 7 段 PASS 已满足，可升级为 `VERIFIED`（但需同步修改 `docs/roadmap/v4.1/功能设计/13_功能需求追踪矩阵FR.md` 的验收描述「Dataset 追溯到 Raw/Session」）。
