# 索引审计（审计 R6）

## 审计假设

> 「408 个索引里可能有零使用索引，成为写放大来源。」（审计报告 R6）

## 结论：**假设不成立——当前无可删索引**

| 判定 | 数量 | 说明 |
|---|---|---|
| 零使用索引总数 | **354** | 占总索引 408 的 87% |
| `keep_constraint` | 225 | 主键/唯一约束背书，**删了约束就没了**，不可删 |
| `review_after_growth` | 129 | 所在表 < 1000 行，PG 一定走 seq scan，索引零使用属正常 |
| **`drop_candidate`** | **0** | **没有任何索引可安全删除** |

**可删候选占用空间：0 字节。**

## 为什么这个结论可信（而不是"统计不准"）

| 检查 | 结果 |
|---|---|
| 索引扫描总量 | **2,847,828** 次 |
| 顺序扫描总量 | 308,422 次 |
| 最热索引 | `ix_outbox_events_dispatch_status` **1,272,514** 次 |
| 统计是否被重置 | `pg_stat_database.stats_reset` 为空（从未重置） |

样本充分且分布明显偏斜——说明 `idx_scan=0` 是真实的"从未被使用"，不是统计缺失。

## 为什么 129 个索引"零使用"仍不该删

这些索引都建在**小表**上（`audit_logs` 39 行、`idempotency_records` 0 行、
`data_lineage_edges` 0 行…）。PostgreSQL 的规划器在小表上一定选顺序扫描——
即使索引存在也不会用。**这是正确行为，不是索引设计错误**。

删掉它们此刻能省一点写成本，但表一旦增长到万级，这些索引就是必需的——
届时重建索引的代价远高于节省的写入开销。因此判定为"表长大后复查"。

## 用可复现的工具替代一次性判断

```bash
# 只读审计（不改任何东西）
python scripts/db/index_audit.py --dsn postgresql+psycopg://ddp:ddp@localhost:55432/ddp

# 机器可读 + 落盘
python scripts/db/index_audit.py --dsn ... --format json --out /tmp/index-audit.json
```

脚本的三条硬规则（防误删）：
1. **样本不足拒绝给结论**：总索引扫描 < 100k 时全部标 `review_after_growth`
2. **约束背书索引永不标可删**：按 `pg_index.indisprimary/indisunique` 区分
3. **小表不算候选**：表行数 < 1000 时 seq scan 更优属正常

判定逻辑有 5 项单测（`backend/tests/unit/test_index_audit_classification.py`），
包括"约束优先级高于样本充分性"这类边界。

## 何时重跑

| 触发条件 | 原因 |
|---|---|
| 单表行数 > 10 万 | 小表豁免失效，索引开始被使用或暴露真实冗余 |
| 生产写入 QPS > 100 | 写放大开始有实际影响 |
| 新增/删除索引的迁移合入后 | 保持审计基线同步 |
| 每季度例行 | 数据增长会改变判定 |

## 诚实边界

- 仅本地单机生产库（数据量最大表 240 行），**不代表有大数据的生产环境**
- `idx_scan` 只统计"索引被用于扫描"，不统计"仅用于约束检查"——约束索引的判定
  已按 `pg_index` 单独处理，但排他约束/部分索引未单独分类
- 未分析索引**冗余**（A 索引是 B 索引前缀）：这需要额外检测，本批未做
- 「可删候选」只意味着"可以评审是否删除"，**不等于建议删除**；删除必须走迁移 + 人工评审
