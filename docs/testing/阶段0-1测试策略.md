## 2. 质量模型与完成定义

### 2.1 质量目标

按风险优先级排序：

1. **数据不被污染**：RawAsset 不可覆盖，Episode/数据集版本可追溯；
2. **权限不越界**：所有项目数据服务端强制 `project_id`，默认拒绝，防 IDOR；
3. **文件不失控**：类型、大小、签名、Hash、路径、分片、断点、幂等、审计可验证；
4. **状态机不越迁**：非法迁移返回 409，终态不可回退，并发有乐观锁；
5. **失败可定位**：结构化日志、request_id、审计、Job 失败记录；
6. **可恢复**：数据库与对象存储备份可恢复，回滚不覆盖数据；
7. **契约不漂移**：OpenAPI、JSON Schema、前端类型、错误码、权限矩阵一致。

### 2.2 五种完成状态（规范 §22.3）

| 状态 | 含义 | 必需证据 | 谁可宣布 |
|---|---|---|---|
| Code Complete | 代码写完 | 分支、提交、PR | 开发 |
| Test Passed | 自动化测试通过 | CI run URL + job 日志 + 统计 | 开发/QA |
| QA Accepted | QA 独立验收通过 | 本文 §5.4 报告 + 证据归档 + 无开放 P0 | QA |
| User Accepted | 用户确认验收 | 平台交付记录/书面确认 | 用户 |
| Released | 已发布 | 发布记录、健康检查、观察窗口 | 用户批准后由发布执行人 |

**硬规则：** 上一状态不能自动推导下一状态；CI 绿不等于 QA Accepted；QA Accepted 不等于 User Accepted；用户未批准不得发布。

### 2.3 风险驱动原则

- P0 风险（数据污染、越权、不可恢复、Secret 泄漏）必须有自动化用例和门禁；无用例即阻断。
- P1 风险（大文件、性能、并发、前端状态）至少有一次真实环境证据或明确豁免。
- P2 风险（体验、非关键告警）可进入技术债登记，但不得静默。
- 阶段 0 只验证“地基”；阶段 1 才验证机器纳管业务。不得把阶段 1 的验收任务提前标记为已通过。

### 2.4 测试替身与证据等级

| 等级 | 定义 | 可用于 | 不可用于 |
|---|---|---|---|
| T0 真实依赖 | 真实 PostgreSQL/Redis/MinIO/浏览器/真实设备 | 集成、E2E、QA Accepted | — |
| T1 真实样例 | 脱敏真实文件/设备包，记录 SHA256 与来源 | 文件处理、数据质量 | 未标注来源的“真实数据” |
| T2 合成样例 | 构造的样例包/模拟 Adapter，显式标注 | 契约、状态机、阶段 1 预演 | 冒充真机验收 |
| T3 测试替身 | Fake/Stub/Mock，显式标注 | 单元、应用层、接口逻辑 | 真实集成/业务验收 |

**规则：** 使用 T2/T3 的测试必须在用例名、文件头或报告“数据来源”字段显式标注；未标注即视为“冒充真实业务验收”，QA 应判 FAIL。

### 4.2 本地命令

在仓库根执行；命令与 CI 等价，后端解释器统一使用 `backend/.venv/bin/python`。

```bash
# 1. 后端 Lint
backend/.venv/bin/ruff check backend/app backend/tests backend/migrations

# 2. 后端测试（显示汇总）
backend/.venv/bin/python -m pytest backend/tests -o addopts=

# 3. 迁移测试（SQLite；PostgreSQL 另见集成门禁）
backend/.venv/bin/python -m pytest backend/tests/migrations -o addopts=

# 4. 前端 Lint / 单测 / 类型 + 构建
npm run lint --prefix apps/web
npm run test --prefix apps/web
npm run build --prefix apps/web

# 5. Secret 扫描
backend/.venv/bin/python scripts/check_secrets.py

# 6. Agent Bash 守卫测试
backend/.venv/bin/python -m pytest scripts/tests -q

# 7. 完整本地检查（当前环境 make 不在 Agent 白名单，需人工执行）
make check
```

`make check` 的顺序为：后端 ruff → pytest → 前端 typecheck/lint/test → 前端 build → Secret → 守卫测试。它与 CI 不完全等价：CI 有 PostgreSQL 迁移步骤、没有统一 JUnit/coverage 归档；阶段 1 必须把两者对齐。

### 4.4 门禁规则

- P0 门禁任一失败：**阻断合并**，不得放宽断言、删除用例、加 `skip/xfail`、改 `continue-on-error` 绕过。
- P1 门禁失败：必须登记缺陷和技术债，指定关闭阶段；阶段 1 起 P1 中的类型/依赖/安全项升级为 P0。
- 豁免：只能由用户书面批准，记录范围、期限、补偿控制、复评日期；QA 不得自行豁免。
- 新增测试只能是“先红后绿”；修复缺陷必须带回归用例。
- 任何契约/迁移/权限变更必须走对应 Owner 评审与 ADR（共享文件单一 Owner）。
- 门禁变更（增删命令、调整阻断级）必须在本文件更新变更记录，并经 QA + Architect 会签。

### 4.5 分支保护与环境

- `main` 走 PR；分支保护在当前 GitHub 账号计划下返回 403（见 `docs/04`），属于 **BLOCKED**，需用户决策升级计划、转公开仓库或接受替代控制。
- 替代控制（待用户批准）：PR 必须附 CI run + QA 复核；CODEOWNERS 会签；合并前人工核对 required checks；禁止直接 push `main` 的本地纪律。
- 环境：local、development、test、staging、production 配置/凭据/数据隔离（规范 §23.3）。staging 与 prod 使用不同 Compose project、端口、数据库、桶。当前 staging 未启动，部署未执行。

5. 观察窗口内的错误率、延迟、积压、上传/处理失败；
6. 回滚点（上一镜像/Compose/迁移 revision）与回滚演练结果；
7. 发布记录归档到 `docs/testing/evidence/`（或平台发布记录）。

**QA 不执行 push、部署、迁移或生产数据操作；发布必须由用户单独批准。**

## 5. 证据要求与 NOT RUN/BLOCKED 口径

### 5.1 证据最小集

每条交付结论至少包含：

| 字段 | 要求 |
|---|---|
| Task ID | 如 DDP-107 |
| Commit | 完整或短 SHA；工作区有未提交改动时注明 |
| 分支/工作树 | 如 `chore/ddp-qa` |
| 环境 | local/test/staging/prod；OS、Python/Node 版本、服务版本 |
| 命令 | 可复制执行的完整命令（含工作目录） |
| 退出码 | 0/非 0 |
| 结果摘要 | 通过/失败/跳过数量、耗时、失败用例名 |
| 原始日志 | CI run URL 或本地日志文件路径；不得只贴截图 |
| 覆盖范围 | 实际覆盖模块/接口/场景 |
| 未覆盖/未验证 | 明确列出 |
| 执行人/时间 | 角色、日期时间（含时区） |

### 5.2 状态口径（强制）

| 状态 | 定义 | 典型场景 |
|---|---|---|
| PASS | 本次实际执行，退出码 0，断言全部通过，证据完整 | `50 passed` + 命令 + 环境 |
| FAIL | 本次实际执行，断言失败或退出码非 0 | 1 failed、构建失败、lint 报错 |
| PARTIAL | 部分子项通过、部分未执行或仅覆盖部分范围；必须逐项列明 | SQLite 迁移通过、PostgreSQL 未跑 |
| NOT RUN | 未执行；或只有历史记录未复跑；或只跑了部分用例；或被测对象尚未实现 | E2E 未安装、依赖扫描未执行 |
| BLOCKED | 因环境、权限、凭据、依赖、设备或策略限制无法执行；已记录阻塞原因、责任人、解除条件 | Docker 被守卫拒绝、分支保护 403、无 staging |

补充规则：

- 不使用 `SKIP` 作为最终状态；pytest 的 `skip/xfail` 必须逐条登记原因，汇总按 `NOT RUN` 计。
- 历史记录（如 `docs/04` 的首轮 CI run）可作为背景，但**本次未复跑即不得标 PASS**。
- Mock/Fake 测试通过只能证明逻辑，不能作为集成/业务验收的 PASS；必须同时标注 T3。
- 只跑单个文件或部分目录，不得声称“全量通过”；必须给全量命令与未跑范围。
- 截图、口头确认、“应该没问题”不构成有效证据。
- 失败不得用修改断言、放宽阈值、删除用例、跳过门禁、降低依赖扫描级别来“修复”。

### 5.3 判定规则

1. 一个交付包含多个门禁时，取最差状态；任一 FAIL 即整体 FAIL；存在 NOT RUN 且属于本阶段必测项，则整体不得 QA Accepted。
2. 阶段门禁要求“全部 P0 PASS、无开放 P0 缺陷、P1 有豁免记录”。
3. 同一用例连续两次失败必须升级缺陷；环境阻塞超过 1 个工作日必须升级 General Owner。
4. 修复缺陷后必须复跑失败用例 + 相邻回归 + 全量 CI；不得只复跑单点。
5. 证据归档路径：`docs/testing/evidence/<YYYY-MM-DD>-<TaskID>/`；至少包含命令、日志、报告、环境说明、结论。

### 5.4 测试报告模板

```markdown
# <Task ID> 测试报告

- 提交/分支：
- 环境：
- 执行人/时间：

## 1. 范围
## 2. 命令与结果
| 门禁 | 命令 | 退出码 | 结果 | 日志 |
## 3. 通过/失败/未执行
## 4. 缺陷
| ID | 严重级 | 现象 | 复现 | 责任角色 | 状态 |
## 5. 未验证范围/风险
## 6. 结论
- 状态：Test Passed / QA Accepted / 不通过
- 是否允许进入下一阶段：
- 回滚点：
```

### 5.5 缺陷移交与阻断

| 严重级 | 定义 | 处理 |
|---|---|---|
| P0 | 数据污染、越权、Secret 泄漏、不可恢复、主链路不可用 | 立即阻断；交对应角色修复；QA 复验；不得豁免 |
| P1 | 关键功能错误、性能不达标、重要安全弱点、证据缺失 | 阻断阶段验收；限期修复或用户书面豁免 |
| P2 | 非关键体验、可维护性、告警噪声 | 登记技术债；指定关闭阶段 |

缺陷必须交回对应角色（Backend/Frontend/Architect/UX），QA 不修改业务代码，也不代为“修绿”。

### 5.6 禁止事项（硬规则）

- 不修改业务代码、配置、数据库、契约；QA 只在 `docs/testing/**` 写文档与证据。
- 不放宽断言、不删除失败测试、不跳过门禁、不把 P0 改为告警。
- 不 push、不部署、不迁移、不改生产数据、不删除数据。
- 不用 Mock 数据冒充真实业务验收。
- 不隐藏失败、不把 `NOT RUN` 写成 `PASS`、不把历史记录写成当前证据。

### 7.4 证据等级与数据要求

- 阶段 1 最低证据等级：**T2 合成样例 + 模拟 Adapter**；必须显式标注“非真机”。
- 有真实设备/脱敏样例时升级为 T1/T0，另行记录来源、SHA256、脱敏范围。
- 无真机不得阻塞契约冻结与权限验收，但 `User Accepted` 前必须说明真机未验证范围。
- 每个文件样本必须有 SHA256、来源、大小、格式、预期结果；恶意样本隔离存放。

### 8.3 偏差与发现

1. **CI 的 PostgreSQL 未被应用测试使用。** `ci.yml` 启动 PG 并设置 `DDP_DATABASE_URL`，但 `backend/tests` 全部显式使用 SQLite 或 Fake；只有 `alembic upgrade head` 使用 PG。阶段 1 必须补真实 PG 集成测试，见 P0-2。
2. **前端类型检查的独立命令未直接跑通。** `npx tsc` 在仓库根解析到了非本地 TypeScript（交互提示），但 `npm run build` 内部的 `tsc --noEmit` 成功；因此字段状态记为 PASS，但 CI 应保留独立 `npm run typecheck` job。
3. **Bash 白名单与 ADR-0008 存在偏差。** ADR 称允许测试/构建/lint/只读 git；实际 `npm run typecheck`、`python3 scripts/check_secrets.py`、`make check`、`alembic`、`docker` 不在白名单或被禁止。`npm run lint/test/build` 与 `backend/.venv/bin/python` 可用。需平台 Owner 与 QA 对齐；守卫测试（23 项）只验证既有规则，不证明白名单覆盖完整。
4. **跨项目语义需冻结。** 现有 API 测试对“非成员访问项目路由”断言 403 `forbidden`；阶段 1 契约区分 403 `project_scope_denied` 与 404 `resource_not_found`。冻结时必须明确兼容策略并补“项目 A 路由访问项目 B 资源 ID → 404”的用例；不得仅改测试迎合现状。
5. **权限 API 测试使用 Fake Service。** 领域/应用逻辑覆盖较好，但真实 PostgreSQL 下的 Repository + API 越权尚未验证；不能据此宣称生产级权限已验收。
6. **前端 bundle 体积警告。** 主 JS 921.20 kB（gzip 296.22 kB），超过 Vite 500 kB 警告线；阶段 1 应评估代码分割，避免把性能问题带入现场弱网环境。
7. **仓库默认凭据。** `Settings` 中 `minioadmin`、`replace-me-in-production` 为本地默认值；必须通过环境变量覆盖，并在部署检查中验证未使用默认值。Secret 扫描通过不代表生产配置安全。
