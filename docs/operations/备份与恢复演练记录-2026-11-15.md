# 备份与恢复演练记录（2026-11-15，含 MinIO 对象恢复）

> 关联：审计 R-4；上一轮记录见 `备份与恢复演练记录-2026-11-14.md`。
> 结论：**PostgreSQL 与 MinIO 都可恢复，且对象内容摘要一致**。
> 脚本可重复执行：`bash scripts/ops/backup-restore-drill.sh`。

## 1. 为什么重做

2026-11-14 的记录里，MinIO 部分只做了一件事：

```bash
OBJ_LIST=$(... command -v mc >/dev/null 2>&1 || exit 0 ... || echo "no-mc")
echo "对象数=${OBJ_LIST}（镜像无 mc 时跳过；S3 数据由 bucket 版本化/异地复制兜底）"
```

两个问题：

1. **`mc` 其实在镜像里**——路径是 `/opt/bitnami/minio-client/bin/mc`，
   不在 `PATH` 上，所以 `command -v mc` 永远失败，这段永远是 `no-mc`，
   等于从来没验证过对象恢复。
2. 即便数列数，也证明不了"能恢复"——恢复演练必须真的**删掉再从备份取回**。

现在桶里已有真实数据（198 个对象 / 221.66 MiB，来自 NVIDIA Human-1M 导入），
可以做有意义的验证了。

| 项 | 值 |
|---|---|
| 数据库 | `ddp-postgres`（healthy），`ddp`，主机端口 55432 |
| 对象存储 | `ddp-minio`（`bitnamilegacy/minio:2025.7.23-debian-12-r5@sha256:6dabb4a2…`，healthy） |

| 恢复方式（对象） | 容器内 `mc mirror` 到 `/tmp/ddp-minio-drill`，抽样删除后 `mc cp` 取回 |
| 演练日期 | 2026-11-15 |

## 4. 这次验证了什么、没验证什么

**验证了**：

- `pg_dump` 产物非空（636 KB）、可完整导入新库；
- 表数 75、迁移版本 `0029`、受检表行数、触发器数 179 在恢复后完全一致——
  说明约束与触发器确实随备份一起恢复，而不是靠代码再装一遍；
- MinIO 全量 198 个对象可以 mirror 出来，字节总量一致；
- **真正删掉一个对象后能从备份恢复**，且 sha256 与删除前相同。

**没验证**：

- 跨机器/异地恢复（本演练全在本机 docker）；
- bucket 版本化与生命周期策略（当前未启用，属阶段 8 的运维项）；
- 备份的加密与访问控制（当前备份落在临时目录，演练后清理）。

## 6. 定时备份（2026-11-15 补）

上述演练是手工执行脚本。同一天新增了维护 worker（ADR-0027），把三件周期性
运维动作变成可调度的进程：

```bash
DDP_MAINTENANCE_ENABLED=true DDP_BACKUP_DIR=/var/backups/ddp \
    python -m app.workers.maintenance --once
```

本机实跑结果：

| 项 | 结果 |
|---|---|
| 产物 | `ddp-20261115T050224Z.sql`，768,007 字节，含 75 个 `CREATE TABLE` |
| 导入独立库 | 成功；恢复后 75 张表 |
| 失败路径 | 连不上库时抛错且不留空文件 |
| 归档边界 | 90 天前 `RECORDED` 删除；`PENDING` / `FAILED` 保留 |

注意：worker **默认关闭**。启用前必须设置 `DDP_BACKUP_DIR` 并挂载持久卷，
否则备份会落在容器临时层；配置校验会拒绝"启用但无备份目录"的启动。
