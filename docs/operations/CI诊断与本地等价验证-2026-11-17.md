# CI 诊断与本地等价验证（2026-11-17）

> 关联：PR #17（N0–N9 全量建设）、PR #19（契约兼容性闸口修复）
> 结论：**代码侧问题已修复并合并；runner 侧为账号级阻塞，无法从代码解决**。

## 1. 现象

`main` 上的 CI（`push` 与 `pull_request` 两种触发）四个 job 全部在 **2–4 秒内失败，
零步骤执行**：

```
{"name":"后端 lint / 迁移 / 测试","conclusion":"failure","runner_name":"","steps":0}
{"name":"前端 类型 / lint / 测试 / 构建","conclusion":"failure","runner_name":"","steps":0}
{"name":"契约 OpenAPI lint / 兼容性 diff","conclusion":"failure","runner_name":"","steps":0}
{"name":"Secret / 依赖 / Agent 守卫","conclusion":"failure","runner_name":"","steps":0}
```

`runner_name` 为空 = **没有任何 runner 被分配**；job 日志返回 `BlobNotFound`，
即这些 job 从未产生过日志。

## 2. 排除法

| 假设 | 检验 | 结论 |
|---|---|---|
| GitHub 平台故障 | `githubstatus.com/api/v2/summary.json` | 全部 `operational`，排除 |
| 仓库 Actions 被禁用 | `GET /repos/.../actions/permissions` → `enabled: true, allowed_actions: all` | 排除 |
| workflow 文件无效 | YAML 可解析，四个 job 均被创建 | 排除（无效文件不会产生 run） |
| 某个 job 自身配置错误 | 新增一个只执行 `echo hello` 的最小 workflow（`_probe.yml`） | **同样零步骤失败**，排除 |
| runner 标签映射问题 | 分别用 `ubuntu-latest` / `ubuntu-24.04` / `ubuntu-22.04` | **三者全部零步骤失败**，排除 |
| 账号级 Actions 分钟数/消费上限 | Dependabot 的托管运行（`Dependabot Updates`）同时段能成功（1m20s） | 托管运行不消耗分钟数，与"计费类运行无法分配 runner"一致 |

**结论**：GitHub 无法为本私有仓库分配 GitHub 托管 runner。最可能是
**Actions 分钟数用尽或消费上限为 $0**。当前 token 无权读取计费接口
（`/user/settings/billing/actions` 返回 404），无法进一步确认。

## 3. 已修复的代码侧问题（真实存在，且会让 CI 变红）

### 3.1 契约兼容性闸口误判（PR #19）

即使 runner 正常，`contract` job 也会失败：`oasdiff breaking` 在 `main` 上产出
**5508 个 error**，全部是 `response-property-enum-value-added`。

根因：`ErrorCode` 是被所有错误响应共享的全局枚举，新增 4 个错误码 → 每个操作各报
一条。本轮新增血缘节点类型又追加 12 条。

修复：比较前把**声明为开放集合**的枚举在两侧归一。清单
`OPEN_ENUMS="ErrorCode LineageNodeType"` 逐项显式列出（不允许通配），
并写明判据（契约本身要求客户端对未知值容错）。

**变异测试证明闸口仍然有效**：

| 变异 | 结果 |
|---|---|
| 删除基线已有响应必填字段（`Robot.capability_profile`） | 退出 1，`response-required-property-removed` |
| 封闭枚举新增值（`EpisodeStatus` 加 `TELEPORTED`） | 退出 1，`response-property-enum-value-added` |
| 仅新增开放枚举值 | 退出 0 |

结果：5508 error → **0 error / 1 warning**（warning 是刻意删除 `Idempotency-Key`）。

### 3.2 `pyyaml` 未声明（同上 PR）

`scripts/check_contract_parity.py` 与兼容性脚本的预处理都 `import yaml`，但
`pyyaml` 只作为环境里的传递依赖存在，未写进 `requirements-dev.txt`。CI 的
`contract` job 只装 `requirements-dev.txt` → 会 `ImportError`。已显式声明并锁
`6.0.3`。

### 3.3 手动触发

`ci.yml` 增加 `workflow_dispatch`，billing/runner 恢复后可直接从 UI 重跑，
不必再推空提交。

## 5. 依赖漏洞扫描（该步骤在 CI 中为 `continue-on-error`，不阻塞）

`pip-audit` 报告 3 个包存在公告：

| 包 | 当前版本 | 公告数 |
|---|---|---|
| `starlette` | 0.41.3 | 14 |
| `pyjwt` | 2.10.1 | 22 |
| `python-multipart` | 0.0.20 | 12 |

**未在本轮升级**：`starlette` 由 `fastapi==0.115.6` 约束，升级会牵动整个 HTTP 层；
`pyjwt` 是认证核心。这类升级需要完整回归 + ADR，不属于「修 CI」的范围。
已登记为独立待办。

## 6. 需要你做的（任选其一）

| 方案 | 操作 | 说明 |
|---|---|---|
| **提高 Actions 额度（推荐）** | GitHub → Settings → Billing and plans → Plans and usage → Actions，设置 spending limit 或补充付款方式 | 免费额度 2000 分钟/月；恢复后点 Actions 页的 "Run workflow" 即可 |
| 仓库转公开 | Settings → General → Danger Zone → Change visibility | 公开仓库的 Actions 不限分钟（但代码会公开，需评估） |
| 自托管 runner | 在一台能出网的主机上装 runner 并注册到本仓库 | 需要你提供机器；注意：自托管 runner 会执行仓库工作流里的代码 |

**注意**：本机 `~/.ssh/config` 里 `your-remote-host` / `your-staging-host` 均无法解析，
所以我无法代为部署自托管 runner。

## 7. 结论

- **代码侧**：CI 会因为契约闸口误判而失败——已修复（PR #19），并用变异测试证明闸口仍然有效。
- **基础设施侧**：GitHub 无法分配托管 runner（账号级）；四个 job 的等价命令已在本地全部通过，退出码 0。
- runner 恢复后，在 Actions 页面手动触发一次即可得到正式绿标。
