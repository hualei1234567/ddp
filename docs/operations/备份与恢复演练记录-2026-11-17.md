# 备份与恢复演练记录（2026-11-17，迁移 0043 + 新增四表结构）

> 关联：N9 完成定义第 4 项「备份恢复和安全检查有演练证据」。
> 上一轮记录见 `备份与恢复演练记录-2026-11-15.md`（迁移 0029）。
> 结论：**PostgreSQL 与 MinIO 都可恢复；本次覆盖 N6/N8/N9 新增的表、列与触发器**。
> 脚本可重复执行：`bash scripts/ops/backup-restore-drill.sh`。

## 1. 为什么必须重做

上次演练停在迁移 `0029`（75 张表 / 179 个触发器）。此后新增了四类采集素材表、
`locations` 表、素材状态守卫触发器、`evaluations.baseline_dataset_version_id`
等结构，迁移链推进到 `0043`。

**备份能不能恢复，取决于当前结构，而不是两个月前那次演练的结论。**
尤其是本轮新增的守卫触发器（素材状态机、训练交付不可变、评测不可变）——
如果它们没随备份一起恢复，恢复出来的库会「看起来数据齐全、实际没有任何
保护」，而这正是审计时最难发现的一类失效。

## 4. 这次验证了什么

- `pg_dump` 产物非空（2.32 MB）且可完整导入独立新库；
- **表数 83、迁移版本 `0043`、12 张受检表行数完全一致**；
- **触发器 188 个在恢复后数量一致**——说明守卫不是靠应用代码重新安装，
  而是随备份一起恢复；
- MinIO 全量 639 个对象 / 654 MiB 可完整 mirror，字节总量一致；
- 真正删掉一个对象后能从备份恢复，sha256 与删除前相同。

## 5. 没验证什么（如实登记）

| 项 | 原因 |
|---|---|
| 跨机器 / 异地恢复 | 演练全在本机 docker，未涉及对象存储异地复制与跨主机网络 |
| bucket 版本化与生命周期 | 当前未启用，属规模化运维项 |
| 备份加密与访问控制 | 演练产物落临时目录并清理；生产需要独立存储位置与保留期 |
| 恢复耗时预算 | 本次数据量小（2.3 MB / 654 MiB），未测大数据量下的 RTO |
| 触发器语义级校验 | 只比对**数量**，未逐条比对各守卫的 `WHEN` 条件正文 |

最后一项需要说明：触发器数量一致不等于守卫内容一致。若某次迁移改写了守卫
条件但保留同名触发器，本演练发现不了。该风险由 `tests/infrastructure/` 下
的守卫行为测试覆盖（直接 UPDATE 断言被拒绝），不是本演练的职责。

## 6. 本次演练顺带确认的部署事实

本地栈此前运行的是 v0.2.0 镜像（head 停在 `0040`）。重建镜像后
`docker compose run migrate` 自动执行了 `0040 → 0041 → 0042 → 0043`，
说明部署链路里 `migrate` 服务按预期在 api 启动前完成迁移。

**这也暴露了一个使用边界**：`migrate` 服务用的是构建时的镜像，镜像不重建，
新增迁移就不会被应用。部署新版本时必须重建镜像——`docker compose up` 会
因 `depends_on: service_completed_successfully` 让人误以为「迁移跑过了」，
实际跑的是旧镜像里的旧迁移。生产发布流程应把镜像重建与 `migrate` 视为一个
原子步骤。
