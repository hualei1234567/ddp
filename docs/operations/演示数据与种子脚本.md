# 演示数据与种子脚本

## 这是什么

`scripts/seed/` 是一套**只走 HTTP API** 的数据种子：按模块把一个真实业务流程从
创建走到终态，把数据留在库里，让界面每个模块都有内容可看。

```bash
backend/.venv/bin/python scripts/seed/run.py            # 全部模块
backend/.venv/bin/python scripts/seed/run.py annotation # 只跑一个
backend/.venv/bin/python scripts/seed/verify.py         # 逐模块核对是否有数据
backend/.venv/bin/python scripts/seed/run.py --list     # 列出模块
```

前置：本地 compose 栈在跑，`.env` 里有 `DDP_WEB_DEV_AUTH`（见
`docs/operations/本地开发令牌.md`）。

## 为什么不直接写数据库

业务规则、状态机、审计、血缘、幂等记录都由服务端产生。直接 INSERT 会造出
「数据库里有、系统里不存在」的假数据：列表能查到，详情点开就崩，审计与血缘
全是空的。种子脚本因此**只调 API**，服务端拒绝就如实报错，不绕过。

唯一例外是 `identity.py`：平台没有注册/用户管理入口（`PLANNED`），
`POST /members` 对不存在的用户返回 404，所以「第二个人」的身份只能由一条
只读查询 + 必要时一条 `users` 插入来准备。

## 纯客户端走不到的终态

> 2026-11-18 更新：下列终态里，采集任务 `DATA_CHECKING`、分配 `EXPIRED`、
> Episode `ARCHIVED`、数据需求 `CLOSED` 都已经有真实触发点，端到端脚本可走到。
> 仍然"纯客户端走不到"的只有三类**系统内部动作**，这是设计口径而非缺口。

| 资源 | 终态 | 触发点 | 状态 |
|---|---|---|---|
| 采集任务 | `DATA_CHECKING` | `domain-worker`（`python -m app.workers.domain_sweeps --interval-seconds 30`）扫到 `SUBMITTED` 后调用系统用例，写 `quality_summary` 并推进 | VERIFIED（`test_collection_task_data_check_advances_to_data_checking`） |
| 采集任务 | `ACCEPTED` / `COMPLETED` | 公开动作 `accept` / `complete`；`complete` 的验收数量从 Episode 事实实时统计 | VERIFIED（`test_collection_task_complete_uses_live_episode_counts`） |
| Episode | `ARCHIVED` | 公开动作 `archive`（`COMPLETED → ARCHIVED`） | VERIFIED（`test_archive_is_reachable_from_completed`） |
| 分配 | `EXPIRED` | `domain-worker` 的租约巡检（`expire_assignments`），执行人取项目负责人并写审计 | VERIFIED（`test_expire_assignments_pushes_claimed_lease_to_expired`） |
| 数据需求 | `CLOSED` | `satisfy → link-retest → close`，复测引用真实评测 | VERIFIED（全链路脚本 `[17]`） |
| Episode | `FAILED` | 只有 `system-fail`，由处理链路失败时写入 | 不对外暴露（设计口径） |
| 评测 / 推理任务 | `SUCCEEDED` | 只能由签名 Adapter 回调推进。**本机已接入 `local-adapter`**，全链路脚本可走到 `SUCCEEDED`；未配置适配器的部署仍会停在 `QUEUED`，这是如实状态 | PARTIAL（依赖部署配置） |
| 训练外部引用 | — | 未配置 `DDP_TRAINING_ADAPTER_ENDPOINTS` 时仍抛 `TrainingAdapterUnavailableError`；本机已配置 `local-training` | PARTIAL（依赖部署配置） |

`docker compose --profile app up -d` 里已包含 `domain-worker`，上述两类系统巡检
随栈常开；只起 `api` 的部署不会推进这两类状态。

## 数据资产生命周期（2026-11-18 补齐）

原始资产状态机里一直有 `post-hoc-quarantine` / `release-quarantine-or-revalidate` /
`reject-quarantined` / `archive` / `tombstone` 五条边，但**没有任何 HTTP 入口**：
被隔离的资产永远放不出来，资产也无法归档或墓碑，界面只能展示用户造不出来的
状态。现已补齐：

| 动作 | 迁移 | 要求 | 触发点 |
|---|---|---|---|
| `post-hoc-quarantine` | VALID → QUARANTINED | 原因 + 至少一个隔离码 | `POST /projects/{p}/raw-assets/{id}/actions/post-hoc-quarantine` |
| `release-quarantine-or-revalidate` | QUARANTINED → VALIDATING | — | 同上；**投递** `ingestion.raw_asset.validation_requested`，由 worker 重新校验 |
| `reject-quarantined` | QUARANTINED → REJECTED | 原因 | 同上 |
| `archive` | VALID → ARCHIVED | — | 同上（归档后仍可下载） |
| `tombstone` | 任意非终态 → TOMBSTONED | 原因 | 同上（只保留元数据与血缘，下载 422） |

`RawAsset` 响应新增 `allowed_actions`，前端只按键渲染；详情页有对应动作条。
端到端验证脚本：

```bash
backend/.venv/bin/python scripts/qa/raw_asset_lifecycle_smoke.py
```

它走真实上传会话 → 真实校验 worker → 隔离 → 放行（重新校验）→ 归档 → 墓碑，
每一步都用服务端的 `allowed_actions` 决定下一步。2026-11-18 实测通过。

**一并调整的产品口径（第 2 项的根因）**

就绪判定不再把"缺标定"当阻塞，只记 notice（单机位 `SINGLE_STREAM_CALIBRATION_ABSENT`、
多机位 `MULTI_STREAM_CALIBRATION_ABSENT`）。原因：公开第一人称数据集普遍多机位且
不带标定，旧口径让它们永远停在 `PENDING`，只能靠 HTTP `ready` 绕过——那正是第 2
项缺陷的成因。标定能否接受由数据集准入的 `CALIBRATION_MISSING` /
`allow_missing_calibration` 显式判断，两件事分开，既不伪造标定也不悄悄放行。

**顺带修掉的基础设施问题**

- 迁移 0052 重装 `annotation_work_guards`（SQLite 的 `CREATE TRIGGER IF NOT EXISTS`
  不会更新既有触发器）；
- 迁移 0052 同时重装 `calibration_profiles` 不可变守卫：SQLite `batch_alter_table`
  重建表会把表上的触发器一起丢掉。

## 数据保留

脚本**不清理任何数据**，重复运行只会新增带新时间戳的记录。想回到干净状态需要
单独批准的重置操作（会删数据，不在本脚本范围内）。

已知副作用：`identity.ensure_reviewer` 会在需要时把既有用户加入项目；
`ensure_second_owner` 会把评审人提升为 owner（数据集授权审批需要第二位负责人），
`projects` 模块结束时恢复到初始角色。

## 技术债

- **`RawAssetLink` 停留在 `PENDING_VERIFICATION`**（2026-11-18 审计发现）：上传完成时
  写入使用关系行（初始 `PENDING_VERIFICATION`），DB 守卫允许迁到 `ACTIVE/REVOKED`，
  但应用层没有任何推进点，也没有读取方。当前不影响血缘查询与数据集构建；若要
  用"使用关系是否已确认"做准入，需要先补推进逻辑。
