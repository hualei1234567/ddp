### 4.2 判断

- 这**不是**「有存量代码待审计」的阶段，而是「绿地建设」阶段。规范 §24 的阶段 0 审计清单中，仓库、技术栈、前后端、数据库、API、权限、文件存储、标注集成、设备集成、部署、CI、测试、运维**全部为 MISSING**。
- 因此阶段 0 的交付重点不是「找可复用模块」，而是：
  1. 把新仓库、CI、契约、环境、平台纳管这些**地基**一次性做对；
  2. 把旧 DDP 的**教训**转化为硬规则，避免重犯；
  3. 明确首批链路的范围，防止一上来铺 16 个领域模块。

### 4.3 旧 DDP 的定位

旧 DDP（2026-10 期间）曾有较大规模：36 路由 / 35 服务 / 22 表模块 / 29 迁移 / 1059+ 后端测试，具备采集、标注、LeRobot、数据集、4090 部署等能力。但：

**结论：旧 DDP 只提供经验与反面教训，不提供可复用代码。新 DDP 必须按新规范重新设计，不能假装"迁移旧系统"。**

## 9. 风险清单

### P0（不解决不能开工）

1. **部署目标未定**：没有可用的 staging/prod 载体，规范要求的发布、回滚、演练无法落地。
2. **平台执行器无 Bash**：自动调度无法完成「改代码 → 跑测试 → 交证据」闭环；只能人工在主会话执行。
3. **GitHub 仓库未建**：规范要求 GitHub 为唯一托管平台，当前无仓库、无分支保护、无 Actions。

### P1（首期必须解决）

4. 技术栈未定：数据库、对象存储、队列、前端框架都未拍板，影响目录、契约和 CI。
5. 无真实设备与样例数据：设备纳管、采集、上传链路只能先用模拟器/样例包，验收证据等级受限。
6. 角色定义缺失：1+6 团队在平台上有角色，但仓库内无 agent 定义，实际执行会退化。
7. 范围过大：16 个领域模块一次铺开必然失控；必须锁定首批链路。
8. 名称冲突：旧 DDP 已废弃，新 DDP 同名，历史文档/记忆/平台残留可能造成误读；需在仓库显著位置声明「新 DDP，与旧 DDP 无关」。

### P2（可后置）

9. 企业 SSO/飞书集成。
10. 多基地、多供应商、成本核算。
11. 模型闭环与自动标注优化。
12. 公网访问与移动端。

## 10. 审计结论

- **可以开工，但要先做阶段 0 基建与三个决策**：部署载体、执行器策略、GitHub 仓库。
