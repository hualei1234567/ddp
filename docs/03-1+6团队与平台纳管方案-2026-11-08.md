# DDP 1+6 智能体团队与平台纳管方案

> 日期：2026-11-08
> 依据：规范 §20（GitHub 协作）、§21（Claude Code Agent 团队）、§22（测试门禁）
> 平台：多项目 Agent 管理平台 `http://xxx.xxx.xxx.xxx:8099`
> 目标：把 DDP 作为独立项目纳入平台，按 1+6 角色组织研发、测试、验收与发布。

---

## 1. 团队编成（1+6）

平台标准模板 `standard-1-6` 已包含全部 7 个角色，角色 key 与 Claude Code `--agent` 对齐：

| 层 | 角色 key | 显示名 | 执行模式 | 必选 | 核心职责 | 产物 |
|---|---|---|---|---|---|---|
| 1 | `general-owner` | General Owner | `main_session` | 是 | 目标统筹、任务拆解、冲突裁决、最终交付 | 阶段计划、任务卡、验收结论 |
| 2 | `product-manager` | Product Manager | `subagent`（只读） | 是 | 需求分析、PRD、优先级、验收标准 | PRD、用户故事、验收标准 |
| 2 | `system-architect` | System Architect | `subagent`（只读） | 是 | 架构、领域模型、API/数据契约、ADR | 架构图、ER 图、OpenAPI、ADR |
| 2 | `ux-designer` | UX Designer | `subagent`（只读） | 是 | 信息架构、流程、交互、视觉规范 | 页面流程、组件规范、设计验收 |
| 3 | `frontend-engineer` | Frontend Engineer | `worktree` | 是 | 页面、组件、接口接入、前端测试 | 前端代码、测试、构建产物 |
| 3 | `backend-engineer` | Backend Engineer | `worktree` | 是 | API、领域服务、数据库、迁移、后端测试 | 后端代码、迁移、测试 |
| 3 | `qa-devops` | QA & DevOps | `readonly`（可配 worktree） | 是 | 测试策略、独立验收、CI/CD、发布、运维 | 测试报告、验收结论、发布记录 |

### 1.1 职责边界（不可越界）

- **PM** 决定「做什么、为什么、怎么验收」，不决定实现方式。
- **Architect** 决定「怎么实现、系统边界、契约」，不替代 PM 定优先级。
- **UX** 决定「用户流程与体验」，不写业务规则。
- **FE/BE** 按冻结契约实现；不得擅自修改共享契约、权限中间件、迁移、全局路由。
- **QA** 独立验证，有权阻断不合格交付；不得为了让测试变绿而放宽断言或删除用例。
- **General Owner** 不能替代专业角色，也不能绕过 QA 宣布验收。

### 1.2 共享契约冻结

以下文件/能力必须由 Architect 冻结，指定唯一 Owner，其他角色不得并行修改：

- `packages/contracts/openapi.yaml`、`packages/contracts/schemas/*.json`
- 数据库迁移目录 `backend/migrations/versions/`
- 权限矩阵 `backend/app/core/security.py` / `permission_map.py`
- 全局路由 `apps/web/src/routes.tsx`
- 设计令牌 `packages/ui/tokens.css`
- 事件契约 `packages/contracts/events/*.json`

变更流程：提出差异 → Architect 评审 → ADR 或契约版本 → 通知所有角色 → 更新测试。

## 2. 工作方式

### 2.1 目录与 worktree

```text
~/vscodeworkspace/DataPlatform/          # 主仓库
├── backend/                             # BE 主工作区
├── apps/web/                            # FE 主工作区
└── packages/...

~/agent-team/ddp-team/
├── worktrees/ddp-be/                    # BE 独立 worktree
├── worktrees/ddp-fe/                    # FE 独立 worktree
├── worktrees/ddp-qa/                    # QA 独立 worktree（只读审查时可不建）
├── reports/                             # 阶段报告（可选）
└── backups/                             # 迁移/发布前备份
```

- 每个可写角色使用独立分支 + worktree。
- 分支命名：`feature/ddp-<task>-<slug>`、`fix/ddp-<task>-<slug>`、`chore/...`。
- 共享文件修改必须由 General Owner 指派单一 Owner。

### 2.2 任务卡模板

```text
Task ID: DDP-000
标题: 初始化后端骨架
Owner: backend-engineer
优先级: P0
目标: ...
背景: ...
输入: 规范章节 / ADR / 契约
输出: 文件、接口、测试、文档
依赖: DDP-xxx
允许修改: backend/app/**, backend/tests/**
禁止修改: packages/contracts/**, apps/web/**, .github/**
API/Schema 约束: ...
验收标准: ...
测试要求: 单元/接口/契约/集成
风险与回滚: ...
```

任务进入平台 `tasks` 表，带 `task_key=DDP-xxx`、`assignee_agent_id`、`priority`、依赖 DAG。

### 2.3 提交与 PR

- Conventional Commits：`feat|fix|refactor|docs|test|perf|build|ci|security`。
- PR 必须包含：关联任务、背景、变更范围、设计说明、DB/API 变更、测试命令与结果、安全影响、风险、回滚方案、文档更新。
- 不使用 `git add -A`；不覆盖其他会话改动；不 `git stash`。
- `main` 分支保护；合并走 PR；发布走标签与平台发布记录。

## 3. 平台纳管步骤（阶段 0 执行）

### 3.1 前置目录

```bash
mkdir -p ~/agent-team/ddp-team/{worktrees,reports,backups}
```

### 3.2 登记项目清单

编辑 `~/agent-workspace/config/projects.json`，追加：

```json
{
  "id": "ddp",
  "code": "ddp",
  "name": "DDP 具身智能数据闭环平台",
  "repo_root": "~/vscodeworkspace/DataPlatform",
  "team_dir": "~/agent-team/ddp-team",
  "default_branch": "main",
  "session_slugs": [
    "-Users-hualei-vscodeworkspace-DataPlatform"
  ]
}
```

> `session_slugs` 必须是 `~/.claude/projects/` 下的精确目录名，平台按精确名单过滤，避免串台。

### 3.3 注册项目（API 或重启自举）

```bash
curl -s -X POST http://xxx.xxx.xxx.xxx:8099/api/projects \
  -H 'Content-Type: application/json' \
  -d '{
    "code": "ddp",
    "name": "DDP 具身智能数据闭环平台",
    "description": "面向具身智能的数据生产、治理、资产化与训练支撑平台",
    "repo_root": "~/vscodeworkspace/DataPlatform",
    "session_slugs": ["-Users-hualei-vscodeworkspace-DataPlatform"],
    "team_template_key": "standard-1-6",
    "owner": "华磊"
  }'
```

或重启平台，`service.bootstrap → ensure_configured_projects` 自动登记并建 7 角色。

### 3.4 应用团队模板

```bash
# 预览
curl -s -X POST http://xxx.xxx.xxx.xxx:8099/api/projects/ddp/team/preview \
  -H 'Content-Type: application/json' -d '{"template_key":"standard-1-6"}'

# 应用（保留实例、幂等）
curl -s -X POST http://xxx.xxx.xxx.xxx:8099/api/projects/ddp/team/apply \
  -H 'Content-Type: application/json' -d '{"template_key":"standard-1-6"}'
```

### 3.5 建立 worktree

```bash
cd ~/vscodeworkspace/DataPlatform
git worktree add ~/agent-team/ddp-team/worktrees/ddp-be -b feature/ddp-be
git worktree add ~/agent-team/ddp-team/worktrees/ddp-fe -b feature/ddp-fe
git worktree add ~/agent-team/ddp-team/worktrees/ddp-qa -b chore/ddp-qa
```

> worktree 必须在 `~/agent-team/ddp-team/worktrees/` 下，平台执行器只允许仓库根或该目录。

### 3.6 创建仓库内 Agent 定义

平台执行器通过 `--agent <role_key>` 启动。若仓库没有 `.claude/agents/<role_key>.md`，会回退 `general-purpose`，角色能力不生效。阶段 0 必须创建：

```text
.claude/agents/general-owner.md
.claude/agents/product-manager.md
.claude/agents/system-architect.md
.claude/agents/ux-designer.md
.claude/agents/frontend-engineer.md
.claude/agents/backend-engineer.md
.claude/agents/qa-devops.md
```

每个文件至少包含：

```markdown
---
name: backend-engineer
description: DDP 后端工程师，负责 API、领域服务、数据库、迁移与后端测试
tools: Read, Glob, Grep, Edit, Write, Bash, TodoWrite
---

你是 DDP 项目的后端工程师。遵守 docs/ 下建设规范与 CLAUDE.md。
只修改被授权的目录；契约变更必须先报 Architect。
所有结论必须附测试命令与结果；未验证必须标注。
```

> `tools` 是否包含 Bash 取决于第 6 节的执行器决策；若平台继续禁用 Bash，则此处写 `Read, Glob, Grep, Edit, Write, TodoWrite`。

### 3.7 任务、知识、评测、发布初始化

- 任务：`DDP-000`～`DDP-012` 按 `docs/02` 建入平台，设置依赖与 assignee。
- 知识：把规范、ADR、OpenAPI、Runbook 发布为 `knowledge items`，供 Agent 检索。
- 评测：建 `unit`、`integration`、`contract`、`e2e`、`security` 五类 eval suite。
- 发布：阶段 0 建一个 `M0-baseline` release 记录，走 validate/evaluation 流程但不发布生产。
- 工作流：建 `feature-delivery`（任务→实现→测试→交付）与 `release`（验证→审批→发布→观察→回滚）两个工作流。
- 运行时：登记 `api`、`web`、`postgres`、`redis`、`minio`、`worker` 六个服务，供健康采集。
- 结果指标：交付周期、CI 通过率、返工率、缺陷逃逸率。

### 3.8 执行开关

平台执行器有两道开关：

1. 全局：`AGWS_PLATFORM_EXECUTOR=on`（默认 `off`）。
2. 项目：`agent_projects.settings_json.execution_enabled = true`（默认 `false`）。

建议：阶段 0 先保持关闭，人工在主会话跑；阶段 1 起按第 6 节策略逐项目开启。

## 4. 角色协作流程

```text
General Owner 拆任务
  → PM 产出需求/验收标准
  → Architect 冻结契约/数据模型
  → UX 出流程/页面规范
  → FE/BE 各自 worktree 实现 + 自测
  → QA 独立验证（测试/安全/性能）
  → General Owner 汇总交付
  → 平台 delivery review/validate
  → 用户验收
  → release validate/evaluation/approval/publish
```

### 4.1 每日/每轮同步

- 平台任务状态：`todo → in_progress → review → done`；阻塞标 `blocked` + 原因。
- 每次交付附：变更摘要、测试命令/结果、未验证范围、风险、回滚点。
- 不隐藏失败；失败尝试保留在 `executions` 与 `dispatch_events`。

### 4.2 冲突裁决

- 契约冲突：Architect 裁决；仍不一致，General Owner 提交用户。
- 范围冲突：PM 提优先级，General Owner 裁决。
- 质量冲突：QA 有阻断权；General Owner 不得绕过。

## 6. 执行器策略差距（必须决策）

### 6.1 现状 `[VERIFIED]`

`~/agent-workspace/app/agent_platform/executor_policy.py`：

```python
ALLOWED_TOOLS = ("Read", "Glob", "Grep", "Edit", "Write", "TodoWrite", "Skill")

argv = [
    "claude", "-p", prompt,
    "--agent", agent_arg,
    "--allowedTools", *allowed_tools,
    "--disallowedTools", "Bash",
    ...
]
```

同时存在 `ALLOWED_BASH_PREFIXES`（pytest、ruff、npm build 等）与 `DENIED_PATTERNS`（push、docker、ssh、migrate 等），但因 `--disallowedTools Bash` 实际失效。

### 6.2 影响

- Agent 能读、写、改代码，但**不能跑测试、构建、lint、git 查询**。
- 用户截图中的 subagent 因请求 `date`/shell 而停滞，正是该策略的直接结果。
- 平台交付无法由 Agent 自证「Test Passed」，只能由主会话补跑，违背规范 §22.3 的证据要求。

### 6.3 选项

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| A 保持禁用 | Agent 只改代码，主会话统一跑测试 | 最安全，零平台改动 | 慢；Agent 无法自验；交付证据链弱 |
| **B 前缀白名单（推荐）** | 为 DDP 项目增加 `execution_tools` 配置，允许 Bash，但只放行测试/构建/lint/只读 git 前缀；继续拒绝 push/deploy/docker/ssh/migrate/删除 | 满足自测；风险可控；复用已有前缀表 | 需小改平台 + 补测试 |
| C 主会话直跑 | 不走平台调度，直接在 Claude Code 主会话开发 | 最快 | 失去平台任务/执行/审计留痕 |

**建议：B。** 具体白名单（仅测试/构建/只读）：

```text
git status|git diff|git log|git show|git branch|git rev-parse|git ls-files
python -m pytest|python3 -m pytest|pytest
python -m py_compile|python3 -m py_compile
ruff check|ruff format --check
npm run build|npm run lint|npm run test|npx tsc|npx vitest run|npx playwright test
ls|cat|head|tail|wc|find|grep|pwd|sed -n
```

禁止：`git push`、`git reset --hard`、`git clean`、`docker`、`ssh`、`scp`、`deploy`、`migrate`、`drop table`、`delete from`、`rm -rf`、`chmod`、`chown`、`sudo`、`curl`、`wget`、越界路径。

### 6.4 实施要求（若选 B）

1. 平台新增项目级字段（如 `settings_json.execution_tools`），默认沿用现状。
2. `build_spec` 按项目配置生成 `--allowedTools` / `--disallowedTools`。
3. 若允许 Bash，必须在同一 argv 中启用权限规则文件或 `--permission-mode`，确保 `check_bash_allowed` 真正生效。
4. 补充平台测试：允许前缀、拒绝模式、跨项目不串配置、默认不放开。
5. 不改变其他项目（material）的行为。

## 9. 明确不做（首期）

- 不建立 GitHub + GitLab 双托管。
- 不引入 DSH / DeepSeek Harness / Codex 作为执行环境。
- 不拆微服务、不引入 CQRS/Event Sourcing。
- 不在 Mac 上做重构建与生产部署（Mac 只做开发与本地验证）。
- 不让多个 Agent 无协调修改共享契约/迁移/权限/路由。
- 不用 Mock 数据冒充真实业务验收；所有 mock 必须显式标注。
- 不在未批准前推送、合并、发布或修改生产数据。
